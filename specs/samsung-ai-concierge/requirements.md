# 요구사항 (Requirements) — 삼성 AI 컨시어지

## 개요

**삼성의 모든 서비스를 도와주는 AI 컨시어지.**
사용자가 무엇이든 AI에게 물어보면 해결해주고, 필요한 제품을 선제안하며,
고장을 미리 알려주고, 해결 방법과 부속품 주문까지 한 번에 이어준다.

### 전체 비전 (장기)
1. **무엇이든 질의응답** — 삼성 서비스 전반에 대해 물어보면 해결
2. **선제적 제품 제안** — 사용자에게 필요한 제품/소모품을 먼저 추천
3. **고장 사전 감지** — 기기 이상을 미리 알려줌
4. **해결 가이드** — 어떻게 고치는지 안내
5. **부속품 간편 주문** — 교체 부품/소모품을 바로 주문

### MVP 범위 (이번 작업) — *확정 필요*
전체 비전 중, **가진 데이터로 끝에서 끝까지 증명 가능한 한 줄기**를 먼저 만든다:

> **"기기 이상 감지 → 원인·해결법 안내 → 필요한 부속품/소모품 주문"** 의
> 대화형 흐름 (위 비전의 3 → 4 → 5, 진입점으로 1의 축소판 포함)

선정 이유:
- SmartThings **개인 API(PAT)는 이미 검증** → 기기 데이터 확보 가능
- CS·제품정보 **실데이터 일부 확보 가능** → 해결법·부품 매칭에 사용
- O2O 로 주문 흐름 연결 (검증 필요)
- 하나의 완결된 가치(고장→해결→주문)를 증명 → 이후 비전 확장의 토대

**MVP 비범위(후속 단계):**
- 선제적 제품 *판매* 추천(비전 2)의 본격 구현 — MVP는 소모품 재주문 알림 수준만
- 삼성 전 서비스에 대한 범용 질의응답(비전 1)의 전면 구현 — MVP는 기기/CS 도메인 한정
- SmartThings **기업 API**, 다계정/조직 단위 운영
- UI 디자인 확정 (디자이너 애셋 수령 전 → 골격/플레이스홀더로 진행)

### 구현 방식 표기 (실 기능 vs Mock)
일부 요구사항은 MVP에서 **Mock(가짜 구현)** 으로 제공하되, **나중에 실 기능으로 교체**한다.
이때 시스템의 나머지 부분이 지금부터 통합할 수 있도록 **인터페이스 경계를 미리 설계**한다.
각 요구사항에 다음 마커를 표기한다:

- **[실 기능]** — MVP에서 실제로 동작
- **[Mock→실]** — MVP는 Mock, 인터페이스는 실 기능 교체를 전제로 설계

## 요구사항 목록

### 요구사항 1: 대화형 질의 진입점

**User Story:**
사용자로서, 자연어로 AI에게 내 기기/제품 관련 질문을 하고 싶다,
그래서 메뉴를 탐색하지 않고도 도움을 받을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 자연어로 질문을 입력하면 THEN 시스템은 의도(기기 상태/문제 해결/주문 등)를 분류해 적절한 흐름으로 연결해야 한다 (SHALL).
2. IF 질문이 MVP 도메인(기기/CS/주문) 밖이면 THEN 시스템은 처리 불가를 명확히 안내하고 가능한 범위를 알려줘야 한다 (SHALL).
3. WHEN 답변에 사용자의 기기 데이터가 필요하면 THEN 시스템은 연동된 SmartThings 계정 데이터를 근거로 응답해야 한다 (SHALL).

### 요구사항 2: 기기 상태 모니터링 및 이상 사전 감지

**User Story:**
사용자로서, 내 기기에 문제가 생기기 전에 알림을 받고 싶다,
그래서 고장으로 인한 불편을 미리 막을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN SmartThings 계정이 연동되면 THEN 시스템은 등록된 기기 목록과 현재 상태를 조회할 수 있어야 한다 (SHALL).
2. WHEN 기기 상태/지표가 이상 기준(예: 소모품 수명, 오류 코드, 비정상 수치)을 충족하면 THEN 시스템은 사용자에게 이상을 알려야 한다 (SHALL).
3. WHEN 이상이 감지되면 THEN 시스템은 어떤 기기의 어떤 문제인지 구체적으로 식별해 제시해야 한다 (SHALL).

### 요구사항 3: 문제 해결 가이드

**User Story:**
사용자로서, 감지되거나 문의한 문제를 어떻게 해결하는지 단계별로 알고 싶다,
그래서 직접 또는 최소한의 도움으로 해결할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 특정 기기 문제가 식별되면 THEN 시스템은 CS 데이터를 근거로 해결 방법을 단계별로 제시해야 한다 (SHALL).
2. IF 해결에 부품/소모품 교체가 필요하면 THEN 시스템은 필요한 부품을 식별해 다음 단계(주문)로 연결해야 한다 (SHALL).
3. IF 사용자가 직접 해결할 수 없는 문제이면 THEN 시스템은 적절한 CS/방문 서비스 경로를 안내해야 한다 (SHALL).

### 요구사항 4: 부속품 / 소모품 주문

**User Story:**
사용자로서, 교체에 필요한 부속품을 복잡한 검색 없이 바로 주문하고 싶다,
그래서 문제를 빠르게 해결할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 필요한 부품이 식별되면 THEN 시스템은 제품정보 데이터에서 해당 기기에 맞는 정확한 부품을 매칭해야 한다 (SHALL).
2. WHEN 사용자가 주문을 진행하면 THEN 시스템은 O2O 경로를 통해 주문(또는 주문 페이지 연결)을 완료할 수 있어야 한다 (SHALL).
3. IF 매칭되는 부품이 없거나 모호하면 THEN 시스템은 임의 선택하지 않고 후보를 제시하거나 확인을 요청해야 한다 (SHALL).

### 요구사항 5: 소모품 재주문 선제안 (선제안의 MVP 형태)

**User Story:**
사용자로서, 소모품 교체 시기가 되면 먼저 알림과 주문 제안을 받고 싶다,
그래서 떨어지기 전에 미리 준비할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 기기 데이터상 소모품 수명/사용량이 임계치에 도달하면 THEN 시스템은 교체 시기를 사용자에게 선제적으로 알려야 한다 (SHALL).
2. WHEN 교체 시기를 알릴 때 THEN 시스템은 해당 소모품의 재주문 동작을 함께 제안해야 한다 (SHALL).

### 요구사항 6: 흐름 중 채팅 전환

**User Story:**
사용자로서, 가이드된 흐름(이상 알림·해결 가이드·주문) 도중에도 자유 채팅으로 전환하고 싶다,
그래서 막히거나 다른 궁금증이 생겨도 끊김 없이 물어볼 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 가이드된 흐름 도중 자유 입력을 하면 THEN 시스템은 채팅 모드로 전환해 응답해야 한다 (SHALL).
2. WHEN 채팅 모드로 전환되면 THEN 시스템은 진행 중이던 흐름의 맥락(대상 기기·문제·주문 상태 등)을 유지해야 한다 (SHALL).
3. WHEN 사용자가 원하면 THEN 시스템은 중단했던 원래 흐름으로 다시 이어서 진행할 수 있어야 한다 (SHALL).

### 요구사항 7: 복합(다중 의도) 질문 처리

**User Story:**
사용자로서, AI 채팅에서 한 번에 여러 가지를 묻고 싶다(예: 의도가 3개 이상),
그래서 같은 내용을 여러 번 나눠 묻지 않아도 된다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자의 질문에 복수 의도(예: 3개 이상)가 포함되면 THEN 시스템은 각 의도를 분해·식별해야 한다 (SHALL).
2. WHEN 복합 질문을 처리할 때 THEN 시스템은 각 의도별로 응답/흐름을 제공하고, 어떤 의도에 답했는지 구분해 제시해야 한다 (SHALL).
3. IF 일부 의도만 처리 가능하면 THEN 시스템은 처리한 것과 처리하지 못한 것을 명확히 구분해 안내해야 한다 (SHALL).

### 요구사항 8: 개인화 정보 기반 추천

**User Story:**
사용자로서, 내 관심사(과거 채팅에서 특정 제품에 관심을 보인 기록)와 보유 기기를 반영한 추천을 받고 싶다,
그래서 나에게 실제로 맞는 제안을 받을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 추천을 생성할 때 THEN 시스템은 사용자의 과거 대화 이력(관심을 보인 제품·주제 등)을 반영해야 한다 (SHALL).
2. WHEN 추천 대상을 선정할 때 THEN 시스템은 사용자가 이미 보유한 기기를 중복 추천하지 않고, 보완·대안 제품을 우선 제시해야 한다 (SHALL).
3. IF 개인화에 쓸 데이터(이력·보유 기기)가 부족하면 THEN 시스템은 일반 추천으로 폴백하되 개인화가 제한적임을 사용자가 알 수 있어야 한다 (SHALL).
4. WHEN 개인화 데이터를 활용할 때 THEN 시스템은 그 근거(예: "이전에 ○○에 관심을 보이셔서")를 함께 제시할 수 있어야 한다 (SHALL).

### 요구사항 9: 주요 화면 및 진입점 (홈 · CS · AI 채팅 패널)

**User Story:**
사용자로서, 홈과 CS 페이지뿐 아니라 어느 화면에서든 AI 채팅 패널에 진입하고 싶다,
그래서 맥락을 잃지 않고 어디서나 바로 도움을 받을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 서비스의 어느 화면에 있든 THEN 시스템은 AI 채팅 패널에 진입할 수 있는 수단을 제공해야 한다 (SHALL).
2. WHEN 사용자가 홈에 첫 진입하면 THEN 시스템은 (개인화된) 주요 제안과 진입점을 제시해야 한다 (SHALL).
3. WHEN 사용자가 CS 페이지에 진입하면 THEN 시스템은 CS 기능(문제 해결·상담 연결·방문 요청 등)으로 연결해야 한다 (SHALL).
4. WHEN 특정 화면에서 채팅 패널을 열면 THEN 시스템은 그 화면의 맥락(보고 있던 제품·기기 등)을 반영할 수 있어야 한다 (SHALL).

### 요구사항 10: 멀티모달 대화

**User Story:**
사용자로서, 텍스트뿐 아니라 이미지·동영상으로 묻고 답을 받고 싶다,
그래서 증상이나 상황을 더 정확히 전달하고 이해할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 이미지·동영상 등 비텍스트 입력을 제공하면 THEN 시스템은 이를 입력으로 처리해 응답에 반영해야 한다 (SHALL).
2. WHEN 시스템이 답변을 제공할 때 THEN 응답 소스에 텍스트 외 이미지·동영상을 포함할 수 있어야 한다 (SHALL).
3. IF 해결 가이드에 시각 자료가 도움이 되면 THEN 시스템은 관련 이미지·동영상을 함께 제시해야 한다 (SHALL).

### 요구사항 11: 응답 템플릿 다양화 및 CTA 연동

**User Story:**
사용자로서, 답변에서 바로 다음 행동(구매·상담·방문 요청)으로 이어가고 싶다,
그래서 별도 페이지를 찾지 않고 끊김 없이 진행할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 답변 유형에 따라 THEN 시스템은 다양한 템플릿(제품 카드·단계별 가이드·비교 등)으로 응답을 구성할 수 있어야 한다 (SHALL).
2. IF 응답이 제품 구매와 관련되면 THEN 시스템은 장바구니 담기·결제 진행 CTA를 제공해야 한다 (SHALL).
3. IF 응답이 CS와 관련되면 THEN 시스템은 상담원 연결·수리기사 방문 요청 등 CTA를 제공해야 한다 (SHALL).
4. WHEN 사용자가 CTA를 실행하면 THEN 시스템은 해당 프로세스(장바구니·결제·상담·방문 요청)로 끊김 없이 연결해야 한다 (SHALL).

### 요구사항 12: 대화 · 이력 저장 및 조회 — [실 기능]

**User Story:**
사용자로서, 이전 대화와 주문·서비스 내역을 다시 보고 싶다,
그래서 맥락을 이어가고 과거에 한 일을 확인할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 대화를 진행하면 THEN 시스템은 대화 맥락을 멀티턴·세션 간에 유지·저장해야 한다 (SHALL).
2. WHEN 사용자가 과거 이력을 요청하면 THEN 시스템은 지난 대화·주문·서비스 요청 내역을 조회해 보여줘야 한다 (SHALL).
3. WHEN 새 대화를 시작할 때 THEN 시스템은 관련된 과거 맥락(보유 기기·진행 중 건 등)을 이어받을 수 있어야 한다 (SHALL).

### 요구사항 13: 장애 · 폴백 처리 — [실 기능]

**User Story:**
사용자로서, 일부 기능이나 연동이 동작하지 않아도 막히지 않고 대안을 받고 싶다,
그래서 어떤 상황에서도 최소한의 도움을 받을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 외부 연동(SmartThings·O2O 등)이 실패하면 THEN 시스템은 오류를 사용자에게 이해 가능한 형태로 알리고 가능한 대안을 제시해야 한다 (SHALL).
2. IF 사용자가 기기를 연동하지 않았거나 데이터가 없으면 THEN 시스템은 기능을 중단하지 않고 일반적인 안내로 폴백해야 한다 (SHALL).
3. WHEN 처리 중 오류가 발생하면 THEN 시스템은 전체 흐름을 깨뜨리지 않고 복구 또는 재시도 경로를 제공해야 한다 (SHALL).

### 요구사항 14: 응답 UX — 스트리밍 및 지연 처리 — [실 기능]

**User Story:**
사용자로서, AI 응답을 기다리는 동안 진행 상태를 보고 싶다,
그래서 멈춘 것처럼 느끼지 않고 긴 답변도 편하게 받을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 시스템이 답변을 생성하면 THEN 응답을 점진적으로(스트리밍) 표시할 수 있어야 한다 (SHALL).
2. WHILE 응답 또는 외부 호출을 처리하는 동안 시스템은 진행 상태(로딩/타이핑 등)를 사용자에게 표시해야 한다 (SHALL).
3. IF 응답이 지연되거나 시간 초과되면 THEN 시스템은 사용자에게 상태를 알리고 다음 행동(대기·재시도·취소)을 제공해야 한다 (SHALL).

### 요구사항 15: 계정 · 기기 연동 / 인증 — [Mock→실]

**User Story:**
사용자로서, 삼성 계정과 SmartThings 기기를 연동하고 싶다,
그래서 내 기기 데이터를 바탕으로 개인화된 도움을 받을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 서비스를 사용하면 THEN 시스템은 인증된 사용자/연동 기기 컨텍스트를 제공해야 한다 (SHALL).
   - *MVP: 고정된 Mock 계정·기기 세트로 제공.*
2. WHEN 기기 데이터에 접근할 때 THEN 시스템은 연동 동의·권한 경계를 통해 접근해야 한다 (SHALL).
   - *MVP: Mock 권한. 인터페이스는 실제 인증·동의 연동으로 교체 가능하게 설계.*

### 요구사항 16: 답변 신뢰성 · 근거 · 불확실성 처리 — [Mock→실]

**User Story:**
사용자로서, AI의 해결 안내가 정확하고 출처가 있다고 믿고 싶다,
그래서 잘못된 안내로 문제를 키우지 않을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 시스템이 해결법·정보를 제시하면 THEN 근거 소스(CS 데이터 등)에 기반하고 출처를 제시할 수 있어야 한다 (SHALL).
2. IF 시스템이 확신할 수 없거나 위험할 수 있는 작업이면 THEN 임의로 단정하지 않고 사람(상담원/기사) 연결로 안내해야 한다 (SHALL).
   - *MVP: 근거·출처·신뢰도 판단을 Mock(고정 규칙/샘플)으로 제공. 인터페이스는 실제 grounding/평가로 교체 가능하게 설계.*

### 요구사항 17: 되돌릴 수 없는 행동 확인 — [Mock→실]

**User Story:**
사용자로서, 결제·주문·방문 요청 같은 중요한 행동은 실행 전에 확인받고 싶다,
그래서 의도하지 않은 처리로 피해를 입지 않을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 결제·주문·방문 요청 등 되돌리기 어려운 CTA를 실행하면 THEN 시스템은 실행 전에 명시적 확인을 받아야 한다 (SHALL).
2. WHEN 확인 후 실행되면 THEN 시스템은 처리 결과를 사용자에게 명확히 알려야 한다 (SHALL).
   - *MVP: 확인 UX는 실제 표시하되, 실제 결제·주문 처리는 Mock. 인터페이스는 실 결제/주문 연동으로 교체 가능하게 설계.*

### 요구사항 18: 사람(상담원 · 기사) 핸드오프 — [Mock→실]

**User Story:**
사용자로서, AI가 못 풀거나 내가 원하면 사람에게 연결되고 싶다,
그래서 끝까지 해결할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN AI가 해결하지 못하거나 사용자가 요청하면 THEN 시스템은 상담원 연결·수리기사 방문 요청 경로로 핸드오프해야 한다 (SHALL).
2. WHEN 핸드오프할 때 THEN 시스템은 진행된 대화 맥락(기기·문제·시도한 해결 등)을 함께 전달해야 한다 (SHALL).
   - *MVP: 핸드오프·맥락 전달을 Mock. 인터페이스는 실제 상담/방문 시스템 연동으로 교체 가능하게 설계.*

### 요구사항 19: 프라이버시 · 동의 · 삭제 — [Mock→실]

**User Story:**
사용자로서, 내 데이터가 어떻게 쓰이는지 통제하고 싶다,
그래서 안심하고 개인화 기능을 사용할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 시스템이 개인화·기기 데이터를 사용할 때 THEN 사용자 동의 범위 안에서만 사용해야 한다 (SHALL).
2. WHEN 사용자가 요청하면 THEN 시스템은 저장된 개인 데이터·이력을 조회·삭제할 수 있어야 한다 (SHALL).
   - *MVP: 동의·삭제를 Mock. 인터페이스는 실제 동의·데이터 관리로 교체 가능하게 설계.*

### 요구사항 20: 선제 알림 전달 · 수신 동의 — [Mock→실]

**User Story:**
사용자로서, 이상·소모품 알림을 원하는 방식으로만 받고 싶다,
그래서 필요한 알림만 받을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 시스템이 선제 알림(이상 감지·소모품 재주문)을 발생시키면 THEN 사용자가 옵트인한 채널로 전달해야 한다 (SHALL).
2. WHEN 사용자가 알림 설정을 변경하면 THEN 시스템은 수신 여부·채널을 반영해야 한다 (SHALL).
   - *MVP: 알림 전달·채널을 Mock(인앱 표시 등). 인터페이스는 실제 푸시·채널 연동으로 교체 가능하게 설계.*
