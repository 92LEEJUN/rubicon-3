# 요구사항 (Requirements) — 정기 점검 리마인더

## 개요
사용자가 기기를 등록·사용해도 **소모품 교체·정기 점검 시점을 스스로 챙기지 못해** 리텐션·기기 건강
기회를 놓친다. 본 작업은 기기별 점검·교체 주기에 도달하면 **선제 리마인더**를 제시해 재관여를
유도한다. 로드맵 Q1 Quick Win(정기 점검 리마인더, S). 선제 재관여는 기존 컴패니언 **엄격
게이트**([ADR-0042](../../docs/adr/0042-companion-proactive-gated.md))를 따르고, 표현은
[response-templates](../../docs/response-templates.md)·open-loop를 재사용한다. design/tasks는 후속.

## 요구사항 목록

### 요구사항 1: 점검 주기 도달 시 리마인더 생성
**User Story:** 사용자로서, 등록한 기기의 점검·소모품 교체 시점이 되면 알림을 받고 싶다, 그래서
적기에 관리할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 기기의 점검/교체 주기(마지막 점검·사용 기준)에 도달하면 THEN 시스템은 해당 사용자에게 **리마인더 항목**(대상 기기·점검 종류·권장 시점)을 생성해야 한다 (SHALL).
2. WHEN 주기에 도달하지 않았으면 THEN 시스템은 리마인더를 생성하지 않아야 한다 (SHALL).
3. 점검 주기·종류는 기기 카탈로그/설정 데이터로 정의되어 결정적이어야 한다 (SHALL).

### 요구사항 2: 선제 제시 게이팅
**User Story:** 사용자로서, 리마인더가 과하거나 부적절한 타이밍에 오지 않기를 원한다, 그래서 알림이
성가시지 않다.

**수용기준 (Acceptance Criteria):**
1. WHEN 리마인더를 선제 제시할 때 THEN 시스템은 기존 컴패니언 선제 게이트(ADR-0042: 빈도·동의·관련성)를 따라야 한다 (SHALL).
2. IF 동일 리마인더를 이미 제시했거나 사용자가 dismiss했으면 THEN 시스템은 중복 제시하지 않아야 한다 (SHALL).
3. WHEN 사용자 동의/알림 scope가 없으면 THEN 시스템은 선제 푸시를 하지 않아야 한다(ADR-0030 동의 scope) (SHALL).

### 요구사항 3: 리마인더 액션
**User Story:** 사용자로서, 리마인더를 받으면 점검을 예약하거나 소모품을 주문하거나 미루고 싶다,
그래서 바로 후속 행동을 할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 리마인더가 제시되면 THEN 시스템은 후속 액션(CTA: 점검 예약·소모품 주문·미루기/끄기)을 제공해야 한다 (SHALL).
2. WHEN 사용자가 후속 액션을 호출하면 THEN 시스템은 기존 예약/주문 커밋 계약(ActionGate)을 따라야 한다 (SHALL).
3. WHEN 사용자가 미루기/끄기를 선택하면 THEN 시스템은 해당 리마인더를 재계산 시점까지 억제해야 한다 (SHALL).

### 요구사항 4: 회귀 불변·토글
**User Story:** 유지보수자로서, 리마인더 기능이 기존 선제·open-loop 동작을 깨지 않기를 원한다.

**수용기준 (Acceptance Criteria):**
1. WHEN 리마인더 기능이 비활성이면 THEN 시스템은 오늘과 동일하게 동작해야 한다 (SHALL).
2. 리마인더 생성·게이팅은 LLM 없이 결정적으로 단위 검증 가능해야 한다 (SHALL).
3. 기존 컴패니언·open-loop 테스트는 통과를 유지해야 한다 (SHALL).
