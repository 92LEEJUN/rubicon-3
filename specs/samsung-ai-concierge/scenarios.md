## 3. 대안 · 분기 시나리오

- **해결 실패 → 핸드오프**(P2) — 가이드로 안 되거나 위험 → 상담원/방문(`handoff_card`·`booking`), 맥락 전달(R18).
- **부품 모호** — 후보 여럿 → `choices`로 사용자 확인, 임의 선택 금지(R4-3).
- **미연동 사용자**(P3) — 기기 데이터 없음 → 일반 안내로 폴백 + 연동 유도(R13-2). *온보딩 흐름 자체는 미정(§5-P).*
- **복합 질문**(R7) — "소리나고 필터도 주문" → 분해 → 우선순위(안전/CS) → 순차 처리.
- **흐름 전환·복원**(R6) — 가이드 중 다른 질문 → 채팅 전환(맥락 유지) → 복귀.

## 4. 엣지 · 예외 시나리오

- **외부 실패** — SmartThings 지연/오류·O2O 실패 → 폴백 안내 + 대안(R13). 대화 중단 금지.
- **권한 거부** — 카메라/갤러리 거부 → 텍스트 입력 폴백(R10·R13).
- **동의 철회 중 개인화** — `Consent.scopes` 밖 접근 거부, 개인화 제한 안내(R19).
- **오탐 흐름 전환** — 자유 입력을 의도 전환으로 오인 → 복원/되돌리기로 완화(design §6.5).
- **결제 실패** — checkout 실패 → 재시도/대안 경로. *결제 특화 복구는 미정(§5-J).*

## 4-B. 시나리오 분류 (Proactive / Reactive / Hybrid)

시나리오를 **누가 시작했는가**로 분류하고, **세션 중 선제 개입**은 속성으로 본다.

### 구분 기준 (3축)
| 축 | Reactive | Proactive |
|----|----------|-----------|
| 트리거 주체 | 사용자(입력·CTA) | 시스템/이벤트 |
| 시간성 | 동기(요청→응답) | 비동기(이벤트·스케줄) |
| 상태 의존 | 요청 시 조회 | **백그라운드 모니터링·텔레메트리 전제** |

### 요구사항 매핑
- **Proactive [P]** — R2·R5·R20·R9-2·R25·**R26·R27**
- **Reactive [R]** — R1·R3·R4·R6·R7·R10·R11·R12·R14·R17·R18·R21·R22·R23·R24
- **Hybrid [H]** — R8(홈=P / 질의=R)

### 위상(phase) — 배타가 아님
1. **P→R 전이** — 선제 알림(P)을 사용자가 탭 → reactive 대화(R). *(메인 저니 1→2단계)*
2. **R 속 P 삽입** — 진단(R) 중 시스템이 먼저 부품 주문·재주문 제안(P).

### Proactive 시나리오 속성 (설계 입력)
선제형은 reactive와 달리 아래 속성을 **명시해야** 한다.

| 요구사항 | 트리거 조건 | 빈도·우선순위 | 동의·채널 |
|----------|-------------|----------------|-----------|
| R2·R5 이상/소모품 | 임계치·오류코드(design §6.3) | 심각도순 | 옵트인(R20) |
| R20 알림 전달 | 알림 발생 | 채널별 | 옵트인·채널 |
| R26 빈도 관리 | 다수 알림 | 묶음·제한 | 사용자 설정 |
| R27 다중 기기 | 동시 이상 | 안전 우선순위 | `home_summary` 묶음 |
| R25 사후 확인 | 해결/주문 완료 후 | 1회성 | 인앱 |

> 선제 파이프라인(텔레메트리→이벤트→임계치→알림)은 `docs/architecture.md` §10 참조.

## 4-C. O2O 시나리오 맵 (양방향)

O2O는 단방향(온라인→오프라인)이 아니라 **reverse(오프라인→온라인)** 가 차별점. 거의 모든 시나리오가
**거점(`Store`/서비스센터) + 슬롯(`Booking`)** 위에 서고, **`Quote`(견적)** 가 오프라인↔온라인을 잇는다.
대부분 **파트너 시스템 연동**이라 MVP는 Mock/비범위.

### A. Online → Offline
| 시나리오 | MVP | 모델 |
|----------|-----|------|
| 가까운 판매처 방문 안내 | 후속 | `StorePort.find_stores`·`Store` |
| 매장 재고 확인 + 픽업(BOPIS) | 후속 | `Order.fulfillment=PICKUP`·`StorePort.check_stock` |
| 체험/데모·오프라인 상담 예약 | 후속 | `BookingSlot`·`Store(EXPERIENCE)` |
| 방문 **설치** 예약 | 후속 | `Booking(visit_type=INSTALL)` |
| 서비스센터 방문 예약 | **MVP(핸드오프 Mock)** | `Booking(SERVICE_CENTER)`·`HandoffPort` |
| 수리기사 방문 요청 | **MVP(핸드오프 Mock)** | `Booking(visit_type=REPAIR)`·R18 |
| 반품/교환 매장 방문·수거 | 후속 | (R21 연계) |

### B. Offline → Online (reverse)
| 시나리오 | MVP | 모델 |
|----------|-----|------|
| 매장 견적/상담 내역 온라인 이어보기 | 후속 | `QuotePort.get_quote`·`Quote(OFFLINE)` |
| 매장 직원 장바구니/견적 앱 전송 | 후속 | `Quote`→`Order` 전환 |
| 오프라인 구매 제품 온라인 등록·연동 | 후속 | 제품 등록 + SmartThings 연동(R15) |
| 오프라인 영수증/주문 이력 통합 | 후속 | `Order` import·보증(R22) 연계 |

### C. 서비스 O2O (A/S)
| 시나리오 | MVP | 모델 |
|----------|-----|------|
| 방문/센터 트리아지(self/기사/센터) | **MVP 일부** | 해결 가이드(R3)·핸드오프(R18) |
| 방문 전 사전 진단·접수 | 부분 | 대화 맥락 전달(R18-2) |
| 수리 견적 사전 확인(유/무상) | **MVP** | `WarrantyPort`(R22) |
| 부품 사전 준비/기사 지참 | 후속 | `Solution.required_parts`·O2O |
| A/S 진행 추적 + 기사 도착 알림 | 부분 | `status_tracker`(R12)·선제알림(R20) |

> **MVP 슬라이스** = 서비스센터/수리 방문 핸드오프(R18, Mock) + 수리 견적 유/무상(R22) + 온라인 주문(R4).
> 나머지(픽업·견적 이어보기·오프라인 통합)는 **후속 O2O 확장**으로 인터페이스(`StorePort`·`QuotePort`)만 미리 둔다.
> 차별 흐름 3종(견적 이어보기·픽업·트리아지)의 **상세 흐름·엣지**는 `design.md` §8, **시퀀스**는 `diagrams.md` §O2O.
