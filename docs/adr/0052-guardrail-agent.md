# ADR-0052: 신뢰·안전을 "별도 가드레일 에이전트"로

- **상태**: 채택
- **관련**: [`specs/trust-safety-baseline/requirements.md`](../../specs/trust-safety-baseline/requirements.md), [agents.md](../agents.md)(§3 조건부 리뷰·§1 슈퍼바이저), [llm-policy.md](../llm-policy.md)(가드레일·어투), [operations.md](../operations.md)(남용·격리), ADR-0011(조건부 리뷰), ADR-0046(안전 게이팅), ADR-0050(신원·커밋 계약)

## 배경
프로덕션 전 필수인 신뢰·안전 계층(레이트리밋·PII 마스킹·프롬프트 인젝션 방어·감사 로그·콘텐츠
가드레일)이 거의 비어 있다(`specs/trust-safety-baseline/requirements.md` R1~R5). 이를 **어디에·어떤
구조로** 넣을지 결정해야 한다. 핵심 긴장은 "기능별 코드에 검사를 흩뿌릴 것인가(인라인)" 대
"검사를 한 곳에 모아 입력/출력 단계로 둘 것인가"이다.

오케스트레이터는 이미 **슈퍼바이저-워커 + 조건부 Review 게이트**(agents.md §1·§3, ADR-0011) 패턴을
갖는다. Review는 최종 직전 안전·근거·정책 검수를 수행하는 **출력측 게이트**다. 신뢰·안전 검사도
본질적으로 "경계에서 입출력을 검사·완화"하는 동형 작업이므로, 이 기존 패턴 위에 얹을 수 있다.

## 결정
신뢰·안전을 **오케스트레이터의 별도 가드레일 에이전트(Guardrail)** 로 둔다. 기능 코드에 인라인하지
않는다.

- **2-단계 검사** — 가드레일은 **입력 단계(pre)** 와 **출력 단계(post)** 의 두 훅으로 동작한다.
  - **입력 검사(pre)** — 플래너/워커 위임 *전*. 레이트리밋(R1, 주로 에지/BFF와 협조)·인젝션 패턴 탐지·
    PII 마스킹(LLM 프롬프트로 가기 전, R2·R3), 외부 콘텐츠 신뢰 경계 격리(R3).
  - **출력 검사(post)** — 최종 방출 *직전*. 콘텐츠 가드레일(llm-policy 금지 규칙, R5)·응답 PII 마스킹·
    안전 게이팅(ADR-0046) 보존.
- **기존 Review 게이트와 정합·통합** — 출력측 가드레일은 agents.md §3 **조건부 Review**의
  안전·근거·정책 검수와 같은 자리(최종 직전 게이트)에 선다. Review가 "근거·정책"을 본다면 가드레일은
  "안전·규정(PII·콘텐츠 정책·인젝션)"을 본다 — 같은 단일 패스 게이트 단계의 **두 관심사**로 묶는다.
  재실행 루프 없이 위반 시 **완화/대체/차단**(무리한 자동 재생성 금지, agents.md §3 정합).
- **감사 로그는 가드레일이 소유** — 보안 의미 이벤트(커밋·게이트 401/409·신원 해석·레이트리밋 차단,
  R4)를 가드레일 단계에서 일관 기록. 감사 레코드는 PII 마스킹(R2)을 따른다.
- **결정적·테스트 가능** — 가드레일 검사는 규칙 기반(정규식·패턴·정책 룰)으로 결정적. LLM 없이 단위
  검증(agents.md §9 정합). 레지스트리(agents.md §12 capability 레지스트리)에 한 엔트리로 추가 가능.
- **회귀 불변·토글** — 안전 토글(`SAFETY` 등) off면 가드레일 미발동 = 오늘과 동일(스트랭글러, R6).

> 이 ADR은 **구조 결정**이다. 구현은 후속. `specs/trust-safety-baseline/`의 design은 이 가드레일
> 에이전트 구조(입력/출력 2-단계 + Review 게이트 통합) **위에서** 설계된다.

## 대안 / 기각
- **인라인(기능 코드마다 검사 호출)** — 각 capability/엔드포인트가 직접 마스킹·검사·로깅. 단순해
  보이나 **검사가 흩어져 누락·드리프트 위험**이 크고, 새 capability마다 재구현해야 하며, 정책의 단일
  출처(llm-policy)와 코드가 어긋난다. **기각** — 횡단 관심사는 한 경계에 모아야 일관·검증 가능.
- **에지 미들웨어 전담(BFF/게이트웨이만)** — 모든 검사를 BFF 레이어에 둔다. 레이트리밋·신원 같은
  **에지 친화 검사(R1)** 에는 적합하나, **LLM 프롬프트 직전 PII 마스킹·인젝션 격리·콘텐츠
  가드레일(R2·R3·R5)** 은 오케스트레이터 내부 맥락(어떤 텍스트가 LLM에 가는가·어떤 출력을 내는가)이
  있어야 정확하다. 에지만으로는 내부 LLM 홉을 보호하지 못함. **부분 채택** — 에지 친화 검사(레이트리밋)는
  BFF/에지와 협조하되, 내용 검사는 가드레일 에이전트가 소유(계층 분담).
- **별도 가드레일 에이전트(채택)** — 검사를 입력/출력 두 경계에 모으고 기존 Review 게이트 패턴과
  통합. 누락·드리프트 최소, 정책 단일 출처와 정합, 결정적 테스트 가능, 레지스트리 한 엔트리로 확장.

## 영향
- **agents.md** — 에이전트 목록에 가드레일이 **횡단 단계(입력 pre / 출력 post)** 로 추가되는 그림.
  Review(조건부)와 같은 게이트 자리에서 협력(별도 워커가 아니라 경계 단계). 본 ADR이 그 근거.
- **llm-policy.md** — 콘텐츠 가드레일(R5)의 금지 규칙 **단일 출처**. 가드레일 에이전트가 이를
  실연동(검사 코드는 정책을 참조, 중복 정의 금지).
- **operations.md** — 레이트리밋·남용 방지(R1)·감사(R4)의 운영 면. 에지/BFF와의 분담(위 부분 채택).
- **계약 영향** — 429(R1)·안전 완화 응답 표현은 FE/BFF가 표현만 함(`specs/trust-safety-baseline`
  R1 비고). 새 봉투 계약 추가 시 3계층 동기화(CLAUDE.md 규칙) — 구현 스펙 design에서 확정.
- 구현은 `specs/trust-safety-baseline/design.md`·`tasks.md`에서 이 구조 위에 상세화(후속).
