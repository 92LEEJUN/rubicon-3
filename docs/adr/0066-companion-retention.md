# ADR-0066: 컴패니언·리텐션 — open-loop 후속 + 재관여 제안(게이트) + 만족도

- **상태**: 채택(스펙 — 구현 후속)
- **관련**: [`specs/companion-retention/`](../../specs/companion-retention/requirements.md), ADR-0042(컴패니언 선제 재관여 = 엄격 게이트), ADR-0029(Engagement vs Analytics), ADR-0030(동의 scope), [operations.md](../operations.md), [`docs/user-journey.md`](../user-journey.md)(V4·P1 알림 피로), R20·R25·R29
- **비고**: 0053~0065 사용 중 → 본 결정은 0066.

## 배경
현재 제품은 **문제 해결로 끝나는 1회성**이다(`docs/user-journey.md` V4). 해결 후 후속·재관여·만족도
루프가 비어 리텐션이 약하다. 반대로 무신경하게 알림을 늘리면 **알림 피로**(P1 좌절)로 역효과다. 기반은
일부 있다 — 선제 재관여 게이트(ADR-0042), Engagement 기록(R29), 미해결 후속(R25), 선제 알림(R20).
이를 **하나의 컴패니언·리텐션 capability**로 묶되 **남발하지 않는** 구조가 필요하다.

## 결정
일회성 보완을 **컴패니언·리텐션** 도메인으로 둔다(Mock 허용). open-loop·재관여는 **이미 구현된
`always-present-companion`을 재사용**(consent-gated, ADR-0042)하고, 본 라운드는 **만족도 수집(추가형)**
과 **자기개선 신호 연결(ADR-0067, `SELF_IMPROVE` 게이트)** 만 더한다 — 기존 동작 불변.

- **Open-loop 추적·후속** — 미해결/후속 필요 스레드를 기록(만료 포함)하고, 적절 시점에 후속 질의 제안을
  만든다("지난번 세탁기 문제 해결됐나요?", R25 위).
- **재관여 제안 + 엄격 게이트** — 트리거(소모품 임박·미해결·점검 시기·재주문 주기)에서 재관여 **제안을
  생성**하되, **자동 노출이 아니라 ADR-0042 게이트**(빈도 상한·중요도·동의 scope R29/R30)를 통과한 것만
  표면화한다. *푸시 남발 금지 = 리텐션의 핵심 안전장치.*
- **만족도 수집** — 해결 확인(R25)에 CSAT/NPS를 인라인으로 수집. 미해결이면 재진단/핸드오프로, 수집 신호는
  **자기개선(ADR-0067) 입력**으로 전달.
- **신호 소유** — 재관여·만족도·open-loop 결과는 Engagement 도메인(R29, analytics와 분리 ADR-0029)에
  기록. 개인화·중복 방지에 재사용.

## 대안 / 기각
- **인라인 알림 남발(게이트 없음)** — 단순하나 알림 피로로 리텐션 역효과. **기각** — 게이트 필수.
- **별도 알림 서비스로 분리** — 실 푸시 채널(roadmap F)은 후속 인프라. 본 ADR은 **제안 생성·게이트·수집**
  도메인 로직까지(채널 배선은 비범위). **부분 채택**.
- **자동 후속을 LLM이 자유 생성** — 환각·남발 위험. **기각** — 트리거+게이트 결정론 우선, 문구만 정책 내.

## 영향
- **operations.md / user-journey.md** — V4(거래→동반자) 실현 경로. P1 알림 피로 완화가 1순위.
- **자기개선(ADR-0067) 연계** — 만족도·미해결·이탈 신호를 개선 제안의 입력으로 공급(두 트랙이 루프로 연결).
- **계약** — 후속/재관여는 기존 §2.1 봉투·기존 template(text·choices 등) 재사용(신규 kind 최소화).
- 구현은 `specs/companion-retention/design.md`·`tasks.md`에서 상세화.
