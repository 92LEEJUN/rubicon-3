# ADR-0035: 데이터 모델 4계층 분리 (DTO / 도메인 / 저장 / Port I/O)

- **상태**: 채택
- **관련**: `docs/data-model.md` §1, ADR-0020

## 배경
같은 개념(예: 기기·주문)이 API 표현·도메인 로직·저장·외부 연동에서 형태가 다르다. 외부 표현 변화가 도메인에 새면 안 되고, 저장소 교체도 쉬워야 한다(ADR-0020).

## 후보안
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | **단일 모델 통합**(어디서나 같은 클래스) | 단순·중복 0 | 외부/저장 변화가 도메인에 직접 전파 |
| B | **DTO만 분리** | API 경계 보호 | 저장·Port 변화는 여전히 누수 |
| **C (선택)** | **4계층 분리** — API DTO / 도메인 / 저장 / Port I/O | 경계별 변화 격리 | 모델 수↑ |

## 결정
**C(실용 절충).** API DTO·Port I/O 타입은 분리해 외부 표현이 도메인에 새지 않게 한다. **MVP는 도메인 ≈ 저장 모델로 단순화 가능**(완전 4종 강제 아님). 외부→도메인 변환은 ACL(ADR-0021).

## 기각 이유
- A: 외부/저장 스키마 변화가 도메인 전반에 전파(ADR-0020 무력화).
- B: 저장·Port 경계 누수가 남는다.

## 결과/영향
계약(api-contract·response-templates)과 1:1 대응하는 FE 타입(`types/`)도 이 경계를 따른다.
