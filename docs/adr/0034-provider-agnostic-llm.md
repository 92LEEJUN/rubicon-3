# ADR-0034: LLM = provider-agnostic + 모델 라우팅

- **상태**: 채택
- **관련**: `docs/architecture.md` §2, `docs/orchestration.md` §1·§6, `backend/app/llm.py`

## 배경
LLM 공급자에 종속되면 전환·비용 최적화가 어렵다. 단순 분류와 복잡 추론의 비용/지연 요구도 다르다.

## 후보안
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | **특정 LLM/SDK에 고정** | 단순·기능 최대 활용 | 종속·전환 비용·비용 최적화 어려움 |
| **B (선택)** | **provider-agnostic 경계** + 모델 라우팅 | 전환 가능·비용/지연 균형 | 공통분모 API로 제한 |

## 결정
**B.** 호출은 "단일 LLM 채팅/메시지 API"의 공통 기능(tool·구조화 출력·스트리밍)만 가정. **비용/지연 균형 모델 기본, 복잡 추론은 상위 모델 라우팅.** `llm.py`가 provider 경계(현재 OpenAI, 교체 가능).

## 기각 이유
- A: 공급자 고정은 비용 급변·전환 시 리스크. 멀티에이전트(ADR-0010)에선 단계별 모델 라우팅이 비용 핵심.

## 결과/영향
모델 라우팅(슈퍼바이저·진단 경량 / 리뷰 상위)은 operations §14·orchestration §6과 연결. 프롬프트 캐싱은 안정 프리픽스(ADR-0013).
