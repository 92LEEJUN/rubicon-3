# 요구사항 (Requirements) — O2O 풀(매장 픽업·재고·견적 이어보기)

## 개요

이 스펙은 컨시어지의 **O2O(Online-to-Offline) 확장**을 다룬다.
현재 MVP는 **온라인 주문(`OrderPort`)만 Mock**으로 동작하고, 매장 거점·픽업 재고(`StorePort`)·
오프라인 견적(`QuotePort`)은 **인터페이스만 선반영**된 상태다(`docs/architecture.md` §5·§12,
`docs/data-model.md` §3·§6). 본 작업은 그 인터페이스 위에서 **온·오프라인을 잇는 실제 동작**을
정의한다:

1. **위치 기반 매장/재고 조회** — 가까운 매장·서비스센터와 픽업 재고 확인.
2. **매장 픽업(BOPIS) 주문 흐름** — 예약(`RESERVED`) → 준비완료 선제 알림(`READY`) → 수령(`PICKED_UP`),
   재고 없음 시 대체 매장/배송 전환.
3. **서비스센터 예약·트리아지** — 셀프 / 기사 방문 / 센터 방문 결정과 사람 핸드오프(R18) 연계.
4. **오프라인 견적 이어보기** — 매장에서 받은 견적을 앱에서 조회하고 온라인 주문으로 전환.

> **기준 정합.** 이 스펙은 **새 요구사항을 만들지 않고**, mvp-concierge의 기존 요구사항
> (R4 주문·R17 확인·R18 핸드오프·R21 취소/환불·R22 보증)을 **O2O 맥락으로 구체화**한다.
> 본 문서의 요구사항 번호(O1~O8)는 이 스펙 안에서만 쓰는 고유 번호이며, 각 항목은
> 대응하는 기반 요구사항(R*)을 함께 표기한다. 공유 데이터 모델·계약은 `docs/`를 참조한다.

### 구현 방식 표기 (실 기능 vs Mock)
mvp-concierge와 동일하게 표기한다.
- **[실 기능]** — MVP/현재에서 실제로 동작(흐름·확인 UX·상태 전이).
- **[Mock→실]** — 현재는 Mock, 인터페이스는 실 파트너 연동 교체를 전제로 설계.

> **O2O 전반의 구현 티어** — `StorePort`·`QuotePort`는 **후속/Mock**, `OrderPort`는 **Mock**,
> `ActionGatePort`는 **확인 UX 실제·처리 Mock**(ADR-0033), `HandoffPort`는 **Mock**이다
> (`docs/architecture.md` §5). 본 스펙은 이 경계를 유지하며, 흐름·상태·확인 UX는 실제로 검증한다.

## 요구사항 목록

### 요구사항 O1: 위치 기반 매장·서비스센터 조회 — [Mock→실]

**User Story:**
사용자로서, 내 위치 근처의 매장과 서비스센터를 찾고 싶다,
그래서 픽업·방문에 편리한 거점을 고를 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 픽업 또는 방문 거점을 찾으려 하면 THEN 시스템은 위치(좌표) 기준으로 가까운
   거점을 조회해 제시해야 한다 (SHALL). (R4·R18)
2. WHEN 거점을 조회할 때 THEN 시스템은 거점 유형(retail / experience / service_center)으로 필터링할
   수 있어야 한다 (SHALL).
3. IF 위치 정보가 없거나 거부되면 THEN 시스템은 흐름을 막지 않고 위치 입력 요청 또는 배송 대안으로
   폴백해야 한다 (SHALL). (R13)
4. WHEN 거점 목록을 제시할 때 THEN 시스템은 각 거점의 이름·유형·주소·(가능 시)운영시간을 함께
   제시해야 한다 (SHALL).

### 요구사항 O2: 픽업 재고 확인 — [Mock→실]

**User Story:**
사용자로서, 특정 매장에 내가 원하는 부품/제품의 재고가 있는지 미리 확인하고 싶다,
그래서 헛걸음 없이 매장에서 바로 받을 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 매장 픽업을 고려하면 THEN 시스템은 선택 대상(부품/제품)에 대해 매장별 픽업 재고
   가용 여부를 확인할 수 있어야 한다 (SHALL). (R4)
2. IF 선택 매장에 재고가 없으면 THEN 시스템은 임의로 진행하지 않고 재고 있는 대체 매장 또는 배송
   전환을 제시해야 한다 (SHALL). (R4-3·R13)
3. WHEN 재고 가용 여부를 제시할 때 THEN 시스템은 재고 없는 거점에서는 픽업 주문 진행을 비활성화해야
   한다 (SHALL).

### 요구사항 O3: 매장 픽업(BOPIS) 주문 흐름 — [Mock→실]

**User Story:**
사용자로서, 부품/제품을 온라인에서 주문하고 가까운 매장에서 받고 싶다,
그래서 배송을 기다리지 않고 빠르게 수령할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 픽업 이행 방식을 선택하면 THEN 시스템은 주문을 픽업(`PICKUP`)·픽업 매장과 함께
   생성하고 픽업 라이프사이클을 `RESERVED`로 시작해야 한다 (SHALL). (R4)
2. WHEN 픽업 주문을 확정하기 직전 THEN 시스템은 되돌릴 수 없는 행동 확인을 받아야 한다 (SHALL). (R17)
3. WHEN 픽업 준비가 완료되면 THEN 시스템은 픽업 상태를 `READY`로 전이하고 사용자에게 준비완료를
   선제적으로 알려야 한다 (SHALL). (R20)
4. WHEN 사용자가 매장에서 수령하면 THEN 시스템은 픽업 상태를 `PICKED_UP`으로 전이해야 한다 (SHALL).
5. WHILE 픽업 주문이 진행 중이면 시스템은 현재 픽업 상태(예약·준비완료·수령)와 픽업 매장을 조회·표시
   할 수 있어야 한다 (SHALL). (R12)
6. WHEN 픽업 상태 전이를 처리할 때 THEN 시스템은 정의된 전이(`RESERVED→READY→PICKED_UP | EXPIRED`)만
   허용하고 역전이를 거부해야 한다 (SHALL).

### 요구사항 O4: 픽업 미수령 만료 · 대체/전환 — [Mock→실]

**User Story:**
사용자로서, 픽업을 못 가거나 재고가 빠지면 자동으로 막히지 않고 대안을 받고 싶다,
그래서 주문이 헛되이 묶이지 않게 하고 싶다.

**수용기준 (Acceptance Criteria):**
1. WHEN 픽업 주문이 정해진 기간 내에 수령되지 않으면 THEN 시스템은 픽업 상태를 `EXPIRED`로 전이하고
   사용자에게 알려야 한다 (SHALL).
2. WHEN 픽업이 `EXPIRED`되면 THEN 시스템은 취소/환불 경로(R21)로 연계해야 한다 (SHALL).
3. IF 픽업 대상 재고가 더 이상 없으면 THEN 시스템은 대체 매장 픽업 또는 배송 전환을 제안해야 한다
   (SHALL). (R13)

### 요구사항 O5: 오프라인 견적 이어보기 — [Mock→실]

**User Story:**
사용자로서, 매장에서 받은 견적을 앱에서 다시 보고 싶다,
그래서 매장을 다시 방문하지 않고도 결정하고 주문으로 이어갈 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 견적 식별자(QR/번호)를 입력/스캔하면 THEN 시스템은 해당 견적(품목·금액·발급 매장)을
   조회해 표시해야 한다 (SHALL).
2. IF 조회하려는 견적이 본인의 것이 아니면 THEN 시스템은 조회를 거부해야 한다 (SHALL).
3. IF 견적이 만료(`EXPIRED`)되었으면 THEN 시스템은 단정하지 않고 재견적 안내를 제공해야 한다 (SHALL).
4. WHEN 견적을 표시할 때 THEN 시스템은 견적 금액과 현재가가 다르거나 일부 품목이 단종/품절이면
   재확인 또는 대체 제안을 제시해야 한다 (SHALL).

### 요구사항 O6: 견적 → 온라인 주문 전환 — [Mock→실]

**User Story:**
사용자로서, 앱에서 본 견적을 그대로 온라인 주문으로 바꾸고 싶다,
그래서 매장 상담 내용을 잃지 않고 끊김 없이 구매할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 활성(`ACTIVE`) 견적을 주문으로 전환하면 THEN 시스템은 확인(R17)을 거쳐 주문을 생성
   하고 견적 상태를 `CONVERTED`로 전이해야 한다 (SHALL). (R4·R17)
2. IF 견적이 `ACTIVE`가 아니면(만료·이미 전환) THEN 시스템은 전환을 거부하고 사유를 안내해야 한다
   (SHALL).
3. WHEN 견적을 전환할 때 THEN 시스템은 전환 시점의 현재가·재고를 검증하고, 차이가 있으면 사용자에게
   고지한 뒤 진행해야 한다 (SHALL).
4. WHEN 견적 전환 주문도 이행 방식을 고를 수 있으면 THEN 시스템은 배송 또는 매장 픽업(O3)을 선택할
   수 있게 해야 한다 (SHALL).

### 요구사항 O7: 서비스 트리아지 · 센터 예약 핸드오프 — [Mock→실]

**User Story:**
사용자로서, 기기 문제를 셀프로 풀지, 기사 방문을 받을지, 센터에 가져갈지 안내받고 싶다,
그래서 가장 적절한 방법으로 해결할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN 기기 증상이 식별되면 THEN 시스템은 셀프 해결 / 출장 수리 / 센터 방문 중 적절한 경로를
   판단해 제시해야 한다 (SHALL). (R3·R18)
2. IF 작업이 위험하거나 셀프에 부적절하면 THEN 시스템은 셀프 진행 대신 기사 방문 또는 센터 방문을
   우선 안내해야 한다 (SHALL). (R23·R16-2)
3. WHEN 트리아지를 안내할 때 THEN 시스템은 보증 상태(유·무상)를 함께 제시할 수 있어야 한다 (SHALL).
   (R22)
4. WHEN 사용자가 센터 방문을 선택하면 THEN 시스템은 방문 거점(서비스센터)과 예약 슬롯을 안내하고
   예약을 생성해야 한다 (SHALL). (R18)
5. WHEN 핸드오프(기사/센터)를 생성할 때 THEN 시스템은 진행된 대화 맥락(기기·증상·시도한 해결)을 함께
   전달해야 한다 (SHALL). (R18)
6. IF 트리아지가 불확실하면 THEN 시스템은 단정하지 않고 상담원 연결로 안내해야 한다 (SHALL). (R16-2)

### 요구사항 O8: O2O 폴백 · Mock↔실 경계 — [실 기능 / Mock→실]

**User Story:**
개발자/운영자로서, 매장·견적 연동이 없거나 실패해도 O2O 흐름이 막히지 않고 실 전환 시 도메인을
건드리지 않게 하고 싶다,
그래서 병렬 개발과 단계적 전환을 안전하게 할 수 있다.

**수용기준 (Acceptance Criteria):**
1. WHEN `StorePort`/`QuotePort` 호출이 실패하거나 미연동이면 THEN 시스템은 전체 흐름을 중단하지 않고
   배송 등 대안 또는 일반 안내로 폴백해야 한다 (SHALL). (R13)
2. WHEN 매장/견적 연동을 Mock에서 실 파트너 시스템으로 교체할 때 THEN 시스템은 도메인 로직 변경 없이
   어댑터 교체만으로 전환할 수 있어야 한다 (SHALL). (ADR-0020)
3. WHEN 픽업/견적 흐름의 되돌릴 수 없는 커밋(픽업 확정·견적 전환·취소)을 처리할 때 THEN 시스템은
   확인 UX는 실제로 수행하고 처리는 Mock으로 시뮬레이션해야 한다 (SHALL). (R17·ADR-0033)
4. WHEN O2O 흐름을 노출할 때 THEN 시스템은 결정적 조회·커밋(매장·재고·견적·픽업)을 `/chat` LLM 경유
   없이 결정적 엔드포인트로 제공해야 한다 (SHALL). (`docs/architecture.md` §8)
