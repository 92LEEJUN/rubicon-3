01시스템 아키텍처

대화 오케스트레이터를 중심에 두고, 도메인 기능은 서비스로, 외부 연동은 어댑터(Port)로 추상화한다. 이 Port 경계가 Mock↔실 교체 지점.

📱 클라이언트 (React Native)홈 · CS · 전역 채팅 패널 / 템플릿·CTA 렌더
▼ WebSocket · HTTP
🔀 API / 표현 계층 (BFF 역할)화면 aggregation · Template 정형화 · 스트리밍 중계 · 인증 게이트
▼ 인프로세스 함수 호출
🧠 대화 오케스트레이터의도 분류·분해 · 흐름(FlowState) · tool 조합 · 세션
▼
⚙️ 도메인 서비스기기 · CS지식 · 카탈로그 · 주문 · 개인화 · 알림
▼
🔌 통합 어댑터 (Port) = Mock↔실 경계SmartThings · O2O · CS · 제품 · Auth · 핸드오프 …
▼
🗄️ 저장소 (Repository)대화·이력 · 세션/맥락 (인메모리 → Postgres+Redis)
단일 진입점 = FastAPI. 별도 BFF 계층은 두지 않고, BFF 책임(aggregation·정형화·스트리밍 중계)은 API/표현 계층이 흡수한다. 분리가 필요해지면(2nd 클라이언트·독립 스케일) 이음새만 떼어내면 된다.
핵심 설계 원칙 · 기술 스택

핵심 원칙

  • 어댑터(Port) 경계로 Mock→실 교체 — 인터페이스 뒤에 Mock을 두어 나머지 시스템은 동일하게 통합.
  • 스트리밍 우선 — 모든 응답 경로는 점진적 전달이 기본(R14).
  • 폴백 내장 — 모든 외부 호출은 실패/미연동 시 대체 경로(R13).
  • 상태 있는 대화 세션 — 흐름 전환·복합 질문·이력을 위해 세션 맥락을 1급으로.
  • UI 디커플링 — 응답은 데이터(템플릿 모델)로, 렌더링은 클라이언트가.

02요청 라우팅 — LLM vs 결정적 경로

FE는 상호작용 유형으로 채널만 고른다. 채널 안에서 "LLM이냐 도메인이냐"는 BE(오케스트레이터)가 결정한다.

의도 분류(하이브리드)
→
LLM 또는 도메인(함수/DB/Port)
대화형 CTA
제안 칩 · 인터랙션 회신 · 설명 요청
→
/chat 재진입
→
LLM 가능 (흐름 재개)
되돌릴 수 없는 커밋
결제 · 주문 · 예약 확정
→
결정적 엔드포인트

→

"CTA = 결정적"이 아니라 "커밋 = 결정적". LLM을 안 타는 건 되돌릴 수 없는 커밋뿐이다(안전성·R17). 제안 칩·선택지 회신·설명 요청 같은 대화형 CTA는 /chat으로 재진입해 LLM을 탈 수 있다.

07API 계약

외부 노출만 HTTP/WS API. 오케스트레이터→도메인은 인프로세스 함수, 데이터는 외부=Port(API)/내부=Repository(DB). 전부 API가 아니다.

WebSocket /chat — 메시지 / 스트림 청크 
# 클라이언트 → 서버
user_message      { session_id, text, media[], screen_context }
interaction_reply { session_id, ref, kind, payload }

# 서버 → 클라이언트 (점진적, R14)
delta     { text }
template  { template }
flow      { active_flow }
done      { message_id, ctas[] }
error     { code, fallback }

WS 봉투 본문은 data-model DTO에 대응(ChatRequest·InteractionReply·ChatResponseChunk).

08LLM 오케스트레이션

의도 처리 → tool 호출 → 근거(RAG) → 응답 생성 → 스트리밍. Claude 단일 Messages API + tool use·구조화 출력 기반.

처리 파이프라인

수신 → ① 의도 분류·분해(하이브리드) → ② 흐름 반영(FlowState)
     → ③ tool 선택·실행 → ④ 근거 보강(RAG) → ⑤ Template 생성 → ⑥ 스트리밍
Tool 레이어 — "전부 API가 아니다"의 실현

LLM에 노출하는 tool은 함수다. 구현 백엔드(API/DB/compute)는 LLM에 안 보인다.

tool구현 백엔드
get_device_statusPort(API) SmartThings
search_solutionsDB/검색 + RAG
match_parts / get_recommendationsDB 카탈로그·이력
get_historyDB(Repository)
create_orderPort O2O + ActionGate(R17)

의도 분류=구조화 출력 + 규칙 가드레일 / RAG=검색→근거 주입→출처 표기. 프롬프트 캐싱·adaptive thinking으로 비용·지연 최적화. 상세: docs/orchestration.md
