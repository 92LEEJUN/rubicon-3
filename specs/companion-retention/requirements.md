# 요구사항 (Requirements) — 컴패니언·리텐션 (일회성 보완)

## 개요
문제 해결로 끝나는 1회성 경험을 **지속 관계**로 보완한다(`docs/user-journey.md` V4). 미해결 스레드를
후속하고, 트리거 기반 재관여를 **엄격 게이트로 남발 없이** 제안하며, 해결 후 만족도를 수집해 개선
루프(ADR-0067)에 공급한다. 전부 토글 `COMPANION` 기본 off=회귀 불변, Mock 허용(실 푸시 채널은 비범위).

## 요구사항 목록

### 요구사항 1: Open-loop 후속
**User Story:** 사용자로서, 지난번 미해결 문제를 시스템이 기억하고 적절히 다시 챙겨주기를 원한다, 그래서
혼자 다시 찾아오지 않아도 된다.

**수용기준:**
1. WHEN 한 턴이 미해결(handoff·해결 미확인·이탈)로 끝날 때 THEN 시스템은 해당 스레드를 **open-loop로
   기록**해야 한다 (SHALL). 만료 기한을 둔다.
2. WHEN 사용자가 다시 진입하고 관련 open-loop가 있을 때 THEN 시스템은 **후속 제안**("지난번 ~ 해결됐나요?")
   을 만들 수 있어야 한다 (SHALL).
3. IF open-loop가 만료되거나 해결 확인되면 THEN 시스템은 그것을 **닫아야** 한다 (SHALL, 재제안 금지).

### 요구사항 2: 재관여 제안 + 엄격 게이트
**User Story:** 사용자로서, 필요한 것(소모품·점검)은 먼저 알려주되 **과한 알림은 받지 않기**를 원한다.

**수용기준:**
1. WHEN 트리거(소모품 임박·미해결·점검 시기·재주문 주기)가 발생할 때 THEN 시스템은 재관여 **제안을
   생성**해야 한다 (SHALL).
2. WHEN 제안은 **ADR-0042 게이트**(빈도 상한·중요도 임계·동의 scope)를 통과한 것만 표면화해야 한다 (SHALL).
   게이트 미통과 제안은 **노출하지 않는다**.
3. IF 사용자가 동의(scope)하지 않았거나 빈도 상한을 넘으면 THEN 시스템은 재관여를 **억제**해야 한다 (SHALL,
   알림 피로 방지).

### 요구사항 3: 만족도 수집
**User Story:** 사용자로서, 해결됐는지 가볍게 확인받고 의견을 줄 수 있기를 원한다.

**수용기준:**
1. WHEN 해결 확인(R25) 시점에 THEN 시스템은 **CSAT/NPS를 인라인으로** 수집할 수 있어야 한다 (SHALL,
   선택 응답·비강제).
2. IF 미해결로 응답하면 THEN 시스템은 **재진단/핸드오프**로 이어야 한다 (SHALL).
3. WHEN 수집된 만족도·미해결·이탈 신호는 **개선 제안 엔진(ADR-0067)의 입력**으로 전달돼야 한다 (SHALL).

### 요구사항 4: 회귀 불변·신호 격리
**수용기준:**
1. WHEN 만족도 수집은 **추가형**(신규 엔드포인트·스토어)이어야 한다 (SHALL) — 기존 경로를 바꾸지 않는다.
   자기개선 신호 emit은 `SELF_IMPROVE` off면 발동하지 않아야 한다(회귀 불변). (기존 후속·재관여는
   consent-gated로 이미 동작 — ADR-0042.)
2. WHEN 재관여·만족도·open-loop 기록은 **Engagement 도메인**(R29, analytics와 분리)에 두어 개인화·중복
   방지에 재사용해야 한다 (SHALL).
