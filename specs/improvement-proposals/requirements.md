# 요구사항 (Requirements) — 개선 제안 엔진 (자기개선, propose-only)

## 개요
제품을 상시 개선하는 피드백 루프(V6)를 **안전하게** 닫는다. 신호를 모아 **증거 기반 개선 제안**을 만들고,
운영자가 검토·승인하면 **S8 실험으로 검증**한 뒤 **사람이 적용**한다. **AI는 자기를 자동으로 고치지
않는다** — 자동 적용 경로 자체가 없다(ADR-0067). 토글 `SELF_IMPROVE` 기본 off=회귀 불변, 결정적·Mock 허용.

## 요구사항 목록

### 요구사항 1: 신호 수집
**User Story:** 운영자로서, 무엇이 잘 안 되는지 흩어진 신호를 한곳에 모아 보기를 원한다.

**수용기준:**
1. WHEN 대화 결과(해결/핸드오프/이탈)·저신뢰 라우팅·clarify 빈발·템플릿 전환율·만족도(ADR-0066)·실험(S8)
   결과를 THEN 시스템은 **신호로 수집**해야 한다 (SHALL). analytics(R28)·Engagement(R29) 재사용.
2. WHEN 수집은 동의·가명화(R28) 범위를 따라야 한다 (SHALL).

### 요구사항 2: 개선 제안 생성 (자동 적용 금지)
**User Story:** 운영자로서, 신호에서 "무엇을 어떻게 바꾸면 좋을지" 구조화된 제안을 받기를 원한다, 그래서
빨리 판단할 수 있다.

**수용기준:**
1. WHEN 패턴(오분류율·저전환·clarify 빈발 등)이 임계를 넘을 때 THEN 시스템은 **구조화 제안**(증거·영향
   추정·변경 후보)을 생성해야 한다 (SHALL).
2. WHEN 시스템은 프롬프트·분류 규칙·템플릿·게이트를 **직접 수정해서는 안 된다** (SHALL NOT). 산출물은 **제안
   뿐**이다(자동 적용 경로 부재 — ADR-0067 불변 원칙).
3. WHEN 제안 생성은 결정론 규칙으로 단위 검증 가능해야 한다 (SHALL, 실 LLM 분석은 선택).

### 요구사항 3: 휴먼 리뷰 큐
**User Story:** 운영자로서, 제안을 검토·승인·기각하고 진행 상태를 추적하기를 원한다.

**수용기준:**
1. WHEN 제안은 **리뷰 큐**에 들어가 상태기계(`제안됨→검토중→승인|기각→검증중→적용`)를 따라야 한다 (SHALL).
2. WHEN **적용은 사람만** 할 수 있어야 한다 (SHALL). 승인/기각/적용은 감사 로그(ADR-0061)에 남는다.
3. IF 제안이 기각되면 THEN 시스템은 그것을 닫고 재생성 시 **중복 억제**해야 한다 (SHALL).

### 요구사항 4: 실험 검증 연계 (S8)
**User Story:** 운영자로서, 승인한 제안이 정말 개선인지 적용 전에 검증하기를 원한다.

**수용기준:**
1. WHEN 제안이 승인될 때 THEN 시스템은 그것을 **S8 실험(ADR-0064)으로 A/B 검증**하도록 연계할 수 있어야
   한다 (SHALL). 검증은 자동, **채택·적용은 사람**.
2. WHEN 검증 결과(지표·승자)는 제안에 첨부돼 사람이 최종 판단해야 한다 (SHALL).

### 요구사항 5: 회귀 불변·내부 한정
**수용기준:**
1. IF `SELF_IMPROVE` 토글이 off이면 THEN 시스템은 수집·제안을 발동하지 않고 기존과 **동일**해야 한다 (SHALL).
2. WHEN 엔진은 **운영 내부 전용**이어야 한다 (SHALL). 사용자 대면 동작·계약은 변경 없다(제안은 백오피스).
