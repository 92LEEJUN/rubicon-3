# 멀티유저 운영 / 스케일 (Operations)

> **기반 문서 (공유).** 멀티유저 환경의 **동시성·병목**, **비용 고려 캐싱**, **세션/상태 격리**,
> **유저별 개인화 컨텍스트 조립**을 정의한다.
> 비기능 제약은 `docs/architecture.md` §7, 오케스트레이션 캐싱·스트리밍은 `docs/orchestration.md` §6·§7,
> LLM 어투·가드레일은 `docs/llm-policy.md` 를 본다. (본 문서는 운영·정합성의 단일 출처)

## 1. 동시성 / 비동기 / 병목

### 현재 상태 (MVP)
- BE 내부 API는 **프로세스 전역 단일 컨테이너**(`build_container()`)와 단일 오케스트레이터를 공유한다
  (`backend/app/api/internal.py`). 인메모리 상태(`MockOrderAdapter._orders`, 예약, Flow*)가 **모든 요청에 공유**되어
  **단일 사용자 가정**이다. → 멀티유저에선 상태 오염/충돌 위험.
- 비동기 경계: **BFF는 async**(FastAPI + `httpx.AsyncClient`)로 I/O 비차단. **BE turn은 동기 제너레이터 + blocking LLM 호출**
  이라, 동시 요청 시 워커/이벤트 루프를 점유할 수 있다.

### 병목 지점
1. **LLM 호출(최대)** — 초 단위 지연 + provider **rate limit(RPM/TPM)**. tool-loop은 N회 왕복이라 지연이 증폭된다.
2. **외부 Port** — SmartThings rate limit·토큰 만료·최종 일관성(architecture §7).
3. **WS 장기 점유** — 스트리밍 커넥션당 메모리/소켓.
4. **공유 인메모리 상태** — 락 경합·교차 오염.

### 대책
- **세션/사용자별 상태 격리** — 컨테이너·FlowState·이력을 **세션 키로 분리**(전역 → 세션 스코프). §3.
- **LLM 동시성 제한·비동기화** — async LLM 클라이언트 + 세마포어/큐로 동시 호출 상한, **백프레셔**. 초과분은 큐잉.
- **tool 왕복 최소화** — 독립 tool **병렬 실행**, tool 결과 캐싱(§2), reasoning effort 하향(단순 분류/조회).
- **타임아웃·취소** — 외부/LLM 타임아웃, 클라이언트 끊김 시 진행 중 LLM 호출 **취소**(낭비 방지).
- **수평 확장** — BFF/BE **무상태화**(상태는 외부 저장)로 인스턴스 증설. WS는 다중 인스턴스 + 공유 세션 저장.
- **레이트리밋/쿼터** — 사용자별 RPM·동시 대화 수 상한(어뷰즈·비용 폭주 방지).
- **멱등성** — 커밋(주문/예약)은 idempotency key로 중복 방지(architecture §7).

## 2. 비용 고려 캐싱 (계층)

LLM·외부 호출 비용을 줄이는 캐시 계층. 각 캐시는 **키·TTL·무효화·정합성** 규칙을 갖는다.

| 계층 | 캐시 대상 | 키 | TTL / 무효화 | 비고 |
|---|---|---|---|---|
| 프롬프트 프리픽스 | system+tools 안정 프리픽스 | 프리픽스 해시 | provider 캐시 수명 | orchestration §6 (휘발성은 뒤로) |
| 의도 분류 | 정규화 입력 → IntentResult | `norm(text)` | 짧게 | 반복 질문 |
| RAG/해결책 검색 | 검색 결과(Solution) | `query·error_code` | 중간 (CS 정적) | orchestration §5 |
| 결정적 조회 | device_status·home_summary | `user·device` | 짧은 TTL (최종 일관성) | SmartThings rate limit 완화 |
| 추천 | `recommend(user)` | `user·interest` | 중간 | Engagement 변경 시 무효(R29) |
| 부품 매칭 | `match_parts` | `model·part_ids` | 길게 (카탈로그 안정) | |
| (선택) 시맨틱 응답 | 유사 질문 답변 | 임베딩 근접 | 주의 | **개인화 응답은 캐시 금지** |

- **개인정보 경계** — 동의·개인화에 의존하는 응답은 **사용자 경계 밖으로 캐시하지 않는다**(R19). 캐시 키에 `user`/`consent` 포함.
- **무효화 트리거** — 기기 상태·주문·예약 변경 이벤트 시 관련 캐시 퍼지. 선제 알림 확인(Engagement) → 추천 캐시 무효.
- **비용 관리** — 경량 모델 라우팅(분류·요약), reasoning effort 조절, **컨텍스트 윈도우 트리밍**(이력 요약), tool 결과 캐시로 왕복 절감.

## 3. 세션 / 상태 격리 (멀티유저)

- **분리 대상** — FlowState(진행 흐름), 대화 이력(R12), 주문/예약 인메모리 상태.
- **저장소** — 세션 맥락 = **휘발성(Redis, TTL)**, 이력·주문 = **영속 DB**(architecture §7).
- **접근 가드** — 모든 데이터 접근은 `user_id` + **Consent 스코프**로 가드(R15·R19). 다른 사용자 컨텍스트 누수 차단.
- **MVP→실 전환** — 전역 컨테이너를 세션 팩토리로 교체(서비스/오케스트레이터 시그니처 불변, architecture §5).

## 4. 유저별 개인화 컨텍스트 조립 (per-user)

사용자마다 다르게 응답하기 위해 프롬프트/도메인에 주입하는 **사용자 컨텍스트**를 정의한다.
(프롬프트 주입·차등 출력 규칙은 `docs/llm-policy.md` §6.)

### 컨텍스트 소스
| 소스 | 용도 | 요구사항 |
|---|---|---|
| 보유/연동 기기·상태 | "내 세탁기" 해석, 보유 기기 중복 추천 방지 | R2·R8-2 |
| 동의 스코프(Consent) | 개인화·기기데이터 사용 가능 여부 | R15·R19 |
| 관심·이력(Engagement·대화) | 추천 근거, 중복 억제 | R8·R29 |
| 프로필(이름·주소·알림 선호) | 호칭·배송·알림 빈도 | R26 |
| 화면 맥락(screen_context) | 보던 기기/제품 반영 | R9-4 |
| 진행 상태(FlowState) | 흐름 이어가기 | R6 |

### 조립 규칙
- **동의 범위 안에서만** 주입. 부족하면 일반 추천 폴백 + 제한 고지(R8-3).
- 토큰 예산 내 **요약·발췌**(전체 이력 금지). 최신·관련 우선.
- 개인식별정보 **최소화**(민감정보 과주입 금지, R19).
- **차등 출력** — 같은 질문이라도 보유 기기·이력·동의에 따라 추천 대상·재주문·근거 문구가 달라진다.

## 5. 관측성 / 비용 추적

- **상관관계 ID**로 대화·tool·주문·핸드오프를 연결(architecture §7).
- 운영 지표: **토큰·호출 수·캐시 적중률·LLM 지연·동시 대화 수**(비용 가시화). 제품 분석(R28, `analytics.md`)과는 별개의 운영 메트릭.

# 동시성 / 큐잉 / 스트리밍 설계 (확정 + 후보안)

> §1~§5의 운영 원칙 위에서, **다량 동시 메시지 처리**에 대한 채택 경로와 후보안을 확정한다.
> 핵심: **인터랙티브(스트리밍)와 비동기(이벤트)를 두 평면으로 분리**한다.

## 6. 동시성 모델 — 채택 경로 A→B, 후보안 C·D

큐와 스트리밍은 상충한다(잡 큐는 토큰 반환 경로가 끊김). 따라서 **2-플레인**으로 나눈다.

- **인터랙티브 평면(저지연·스트리밍)** — 채팅 turn. WS → **동시성 제한 워커** → LLM 스트림 → **같은 연결로 토큰 반환**.
- **비동기 평면(내구성 큐)** — 선제 알림·주문/예약 후처리·분석·미디어 생성·재시도/DLQ.

### 채택 경로
- **Phase A (인프로세스, 즉시)** — `asyncio` 세마포어로 **LLM 동시 호출 상한** + 큐(`asyncio.Queue`). 인프라 0. 단일 프로세스·비내구성 한계.
- **Phase B (Redis, 채택 목표)** — Redis로 ① **세션 상태 격리(TTL)** ② **토큰버킷 레이트리밋(RPM/TPM)** ③ **pub/sub 스트리밍 릴레이**(워커→WS 서버, 무상태 수평확장). 인터랙티브 평면의 경량 큐로 Redis Streams 사용 가능.

> Phase A→B까지를 실제 구현 대상으로 한다. 아래 C·D는 **비동기 평면이 커질 때의 후보안**(지금 도입 X).

### Phase A 실행 계획 (확정)
실측(§14-1: 복합 ~21s) 기반으로 다음 순서·실행 모델을 확정:
- **실행 모델 = async 전환(목표)** — openai async 클라이언트 + `asyncio.gather`(병렬·fine abort 정합, BFF·Phase B와 일관). 단 아래 2a는 BFF-only라 **async 리팩터 없이 선행**한다.
- **순서** — ① **2a 증분 스트리밍**(BFF 버퍼링→포워딩, 저위험·즉효, 단일 경로도 이득) → ② **후보 1 병렬화**(진단∥커머스, async 기반, ~35%↓) → ③ **후보 3 타임아웃·부분폴백·끊김 abort**(async = fine abort).
- **이번 스트리밍 범위 = 2a만** — 결정적 프리페치/다단계 섹션(2b)은 후속(첫 섹션 ≤2~3s 목표는 2b에서).
- **abort 입도** — async 전환 후 **fine abort**(in-flight 취소). 2a 단계에선 적용 안 함.

### 후보안 C — Kafka (비동기 평면, 이벤트 백본)
- **용도** — 선제 알림·주문/예약 이벤트·분석 이벤트·미디어 생성 잡·DLQ 등 **내구성·재처리·다중 소비자 fan-out**이 필요한 비동기 처리. **인터랙티브 채팅 응답 경로엔 두지 않는다**(지연↑, 스트리밍 복잡).
- **토픽/파티션(예시)** — `alerts`·`order-events`·`analytics-events`·`media-jobs`·`*.dlq`. **파티션 키 = user_id(또는 session_id)** 로 **사용자 단위 순서 보장**.
- **소비** — consumer group으로 워커 수평확장, **offset 재처리**로 장애 복구·백필. 스키마는 **레지스트리/버전관리**(이벤트 계약 진화).
- **트레이드오프** — 내구성·고처리량·순서(파티션 내) ↔ 운영 부담·지연·인프라 비용.
- **도입 트리거** — 이벤트량 급증, 다중 소비자(알림+분석+검색 인덱싱), 재처리/감사 요구.

### 후보안 D — 매니지드 (서버리스)
- **구성** — **SQS(FIFO) + Lambda 워커** 또는 **Cloud Pub/Sub**. FIFO 큐로 그룹(session) 순서 + **가시성 타임아웃·DLQ**.
- **트레이드오프** — 운영 최소·오토스케일 ↔ **벤더 락인**, **스트리밍 별도 설계**, 콜드스타트 지연.
- **도입 트리거** — 운영 인력 최소화·트래픽 스파이크가 큰 서버리스 지향 환경.

## 7. 세션 단위 직렬화 — 응답 중 입력 차단 (확정)

- **같은 사용자의 메시지는 순서 보장.** 1차 정책은 **FE에서 응답 생성 중 입력/전송 차단**(현재 `ChatPanel`이 `streaming` 동안 입력·전송 비활성과 동일). → 같은 세션의 **동시/추월 메시지가 애초에 발생하지 않음**.
- **서버 방어선** — 세션 키 단위 직렬화(세션 락/세션 큐)로 우회 입력(다중 탭·재연결)도 순서 보장. 한 세션은 동시에 1개 turn만 처리.
- **세션 간**은 병렬(서로 영향 없음). 격리는 §3.

## 8. 실패 처리 / Retry

- **에러 분류** — 일시적(429·5xx·타임아웃) → **지수 백오프 + 지터** 재시도 / 영구적(검증 4xx·콘텐츠 정책) → 재시도 금지·폴백.
- **레이트리밋 선제** — 워커 공유 **토큰버킷(Redis)** 으로 RPM/TPM 아래 유지, 한계 근접 시 **인터랙티브 평면은 §9·§11로 흡수**(429 맞기 전에 차단).
- **멱등성** — 주문/예약 커밋은 **idempotency key**(재시도 중복 방지, architecture §7).
- **서킷 브레이커** — OpenAI·SmartThings별 연속 실패 시 open → 빠른 폴백(결정적 템플릿/안내), half-open 복구.
- **DLQ** — 비동기 잡 재시도 소진 시 데드레터 + 알림.
- **스트리밍 중 실패** — 첫 토큰 전이면 조용히 재시도. **토큰 전송 후** 실패는 되돌릴 수 없으니 **에러 + "다시 생성"** 제공(부분 결과 보존).

## 9. 텍스트 스트리밍 (증분)

- 인터랙티브 평면은 **delta 토큰 스트리밍 유지**(R14). 현재 BFF `turn_chunks`는 **청크를 다 모아 전달(버퍼링)** → **증분 포워딩(async generator)** 으로 개선해 토큰 단위 중계.
- Phase B에서 워커가 분리되면 **Redis 채널(세션/turn 키)** 에 delta publish → WS 서버가 구독해 흘려보냄(다중 인스턴스 동작).

## 10. 미디어 점진 표시 (플레이스홀더 → 지연 로드)

- 텍스트는 먼저 끝나도 **미디어는 뒤따라** 채워진다(텍스트 블로킹 X).
- 템플릿 미디어를 **참조+상태**로 확장: `media:[{type, ref, status:'pending'|'ready', url?, blurhash?}]`(→ `response-templates.md` 반영 대상).
- FE는 **즉시 플레이스홀더**(스켈레톤/blurhash/LQIP) 렌더 → 준비되면 스왑(현 `Thumb`: URL 있으면 Image, 없으면 플레이스홀더 — 토대 존재). 영상은 **포스터 먼저 → 스트림**.
- 무거운/생성 미디어는 **비동기 평면 잡**(§6) → CDN/서명 URL 생성 → **"media ready" 이벤트/섹션 업데이트**로 FE 도착.

## 11. 백프레셔 UX — 무노출 · 점진 렌더 (확정)

- **혼잡·대기·순번·"다른 사용자 때문" 신호를 일절 노출하지 않는다.**
- **점진 렌더**로 체감 지연을 가린다: 빠른 **결정적 섹션(device_status 등)·스켈레톤을 즉시** 띄우고 **LLM 텍스트는 뒤이어 스트리밍**. 사용자는 "유용한 내용이 바로 나오고 글이 차오르는" 것으로 인지.
- **인디케이터 문구 규칙** — 항상 **답변 중심**("답변을 정리하고 있어요")만. **시스템·대기·순번·혼잡 언급 금지.**
- (참고) "적응형 강등(경량 모델/결정적 전환)"은 이번 채택에서 제외 — **품질 일관성 우선**. 추후 후보로만 남김.

## 12. SLA / 취소 / 우선순위 (확정)

> 전제: 능동 강등 제외(품질 일관성), 대기·순번 무노출(§11 점진 렌더), 세션 추월은 입력 차단(§7).

- **SLA 성격** — 능동 강등으로 맞추지 않으므로 **목표 + 관측 + 오토스케일 트리거**로 운영(요청 내부 품질 저하 없음).
  - 목표값(초안, 실측 튜닝): **첫 토큰 p95 ≤ 2s · 완료 p95 ≤ 12s**(LLM 경로) / 결정적 조회 p95 ≤ 300ms.
- **과부하 정책 = 수용 + 점진 렌더 + 오토스케일** — 대기/순번 노출 없이 받아 처리, **워커 오토스케일**(동시성·큐깊이·p95 기반)로 해소.
  - **보호용 하드캡** — 붕괴 방지 상한 도달 시에만 **소프트 폴백**(결정적/안내). 이때도 순번·혼잡 언급 금지(§11).
- **우선순위 클래스** — 인터랙티브(높음) > 비동기/선제·분석·미디어(낮음). 비동기 평면은 지연 허용·자유 큐잉. 인터랙티브 내부는 단일 등급(MVP).
- **취소 / 타임아웃** — ⓐ WS 끊김 → 진행 중 LLM **abort**(비용 절감) ⓑ **타임아웃 초과 → abort + 폴백**(R13). 같은 세션 supersede 불필요(§7).
- **남은 확정(구현 단계)** — SLA 목표값 실측 튜닝, 하드캡 임계, 오토스케일 메트릭/임계, 비동기 평면 데드라인.

## 13. Phase B (Redis) 설계 (확정)

**토폴로지 — BFF가 WS 종단·릴레이, BE는 무상태 워커**(현 3계층 유지):
```text
client ⇄ [BFF: WS 종단] ⇄ Redis(세션·락·레이트리밋·잡큐·릴레이) ⇄ [BE: 무상태 워커] ⇄ DB
```

**Redis 책임 + 키 스킴(초안):**

| 책임 | 키 / 구조 | 메모 |
|---|---|---|
| 세션 상태 격리 | `sess:{sid}` JSON(user_id·FlowState·screen_context·last_active) | **TTL 30m 슬라이딩**. 워커는 여기서만 읽어 무상태화 |
| 세션 직렬화 락 | `lock:turn:{sid}` (SET NX PX) | 세션당 동시 1 turn(§7 서버 방어선). PX 만료로 데드락 방지 |
| 레이트리밋(토큰버킷) | `rl:openai:{rpm,tpm}`(전역) · `rl:user:{uid}:rpm`(공정성) | **Lua 스크립트**로 원자적 refill+consume |
| 잡 큐 | `q:turns` (Streams + consumer group `workers`) | 인터랙티브 turn 분배·수평확장 |
| 스트리밍 릴레이 | 채널 키 = `turn_id` | **메커니즘 결정 보류**(아래) |

**스트리밍 릴레이 — 결정 보류(구현 시 벤치 후 택1):**
- **Redis Streams**(XADD/XREAD·consumer group) — 첫 토큰 유실 없음·재연결 재생·견고. 약간 복잡.
- **Pub/Sub** — 단순. 구독 전 발행되면 유실·재생 불가(구독→인큐 순서로 완화 필요).

**turn 시퀀스:**
1. **BFF** — 입력 수신 → `lock:turn:{sid}` 획득 → `turn_id` 발급 → `q:turns` 인큐 → 릴레이 **구독 시작**.
2. **BE 워커** — 잡 수신 → 토큰버킷 통과 대기 → `sess:{sid}` 로드 → LLM tool-loop → delta를 릴레이로 → done.
3. **BFF** — delta 포워딩(증분 §9) → done에 **락 해제·스트림 정리**.
4. **끊김/타임아웃** — BFF가 cancel 신호(`cancel:{turn_id}`) → 워커가 청크 사이에서 **abort**(§12).

**무상태 · 복구:** 워커 크래시 → consumer group pending → **XCLAIM 재처리** 또는 DLQ→에러+재생성(§8). 모든 상태는 Redis/DB.

**비범위(구현 단계):** 릴레이 메커니즘 최종 선택, Lua 토큰버킷 세부, 오토스케일 메트릭/임계, TTL·하드캡 실측값.

## 14. 멀티에이전트 지연 고려 (supervisor · search · review + DB)

> 멀티에이전트(orchestration §10)는 LLM 호출 직렬 누적으로 **7~15s**가 난다. 뼈대(2-플레인·세션격리·세마포어·
> 백프레셔 무노출)는 **유효**하되, 아래가 추가된다.

- **SLA 재정의 — 완료시간 단일 목표 → 진행 지표 분해**:
  - **첫 의미있는 섹션 ≤ 2~3s**(DB/결정적 우선) ← 멀티에이전트 SLA의 핵심 지표.
  - 단계 진행 이벤트가 끊기지 않을 것(다단계 스트리밍, orchestration §10).
  - **완료는 별도 등급** — 복합/멀티에이전트 p95 ≤ **15~20s**(§12의 단일 ≤12s는 단일 경로 기준).
- **동시성·비용 N배** — 워커가 **7~15s 점유** + 턴당 **LLM 호출 3~5회**:
  - 워커당 **동시성 상한↓**, **오토스케일 더 일찍**(홀드타임 반영).
  - provider 레이트리밋 압력 **×N** → 토큰버킷(§13)·캐싱(§2)·**모델 라우팅** 중요도↑.
  - 블로킹 스레드 점유가 N배 → **Phase B(무상태 워커 분리) 시급성↑**.
- **단계별 타임아웃 + 부분 폴백** — 글로벌 1개 → **에이전트 단계별**. 초과 시 부분결과 반환(R13). 끊김 abort 가치 **×N**(§12).
- **릴레이** — 멀티에이전트 **다단계 순서 이벤트**가 많아 **Redis Streams에 유리**(§13). **단 최종 선택은 보류 유지.**
- **관측성** — 에이전트별 **스팬·단계 지연**(슈퍼바이저·서치·리뷰·DB) 분해 추적으로 병목 식별(§5 확장).

### 14-1. 실측 (gpt-4o-mini, Mock tool, 순차)

`backend/app/orchestrator/multiagent.py`(슈퍼바이저→진단→커머스→조건부 리뷰)로 실측한 값:

| 케이스 | 총 지연 | LLM 호출 | 단계 분해 |
|---|---|---|---|
| 단순(진단만) | ~6s | 3 | supervisor ~1.5s + diagnosis ~4.5s |
| **복합(진단+주문+리뷰)** | **15~21s** (평균 ~18s, **최대 ~21s**) | 6~7 | supervisor ~1s + diagnosis 6~10s + commerce 4~7s + review 3~4s |

- **최대 단일 LLM 라운드트립 ~6.6s** (tool-loop 내). 툴콜(Mock) 자체는 1ms 미만 — **지연은 전부 LLM 왕복**.
- 복합 실측(~21s)이 **§14의 15~20s 등급 상단을 초과** → 두 레버가 그래서 중요:
  - **턴 내 병렬화**(orchestration §10) — 진단∥커머스 병렬 시 `supervisor + max(diag, comm) + review`로, 위 케이스 ~21s → **~13s** 추정(약 35%↓).
  - **다단계 스트리밍** — 첫 섹션 ≤ 2~3s(§14)로 체감 지연을 가린다(총 완료가 길어도 빈 대기 방지).
- Phase A 적용분: 모든 LLM 호출이 `llm.chat_completion`(동시성 세마포어 `LLM_MAX_CONCURRENCY` + 429/5xx 지수 백오프+지터)을 경유.
