# 요구사항 (Requirements) — 개인정보/규제(Privacy·DSR)

## 개요
GDPR·개인정보보호법(PIPA) 대응을 위한 **개인정보·데이터 주체 요청(DSR)** 스트림(S5)이다.
기존 동의(Consent, ADR-0030) 모델 위에 **scope별 부여/철회**를 더하고, 데이터 주체 요청
워크플로(**접근/내보내기·삭제·정정**)와 **보존(retention) 정책 + 만료 스윕 인터페이스(Mock)**,
**감사(audit) 훅**을 제공한다. 모든 기능은 **추가형**이며 기본 동작을 바꾸지 않는다(회귀 불변).
상태 저장소는 이미 `user_id`로 키잉돼 있어, DSR은 그 키로 데이터를 모으고/지우는 형태로 구현한다.

## 요구사항 목록

### 요구사항 1: scope별 동의 부여/철회

**User Story:**
사용자로서, 기능별 동의(scope)를 개별적으로 부여하거나 철회하기를 원한다,
그래서 일부만 허용하고 나머지는 거부할 수 있다(ADR-0030).

**수용기준 (Acceptance Criteria):**
1. WHEN 사용자가 특정 scope(예: `personalization`)에 동의를 부여하면 THEN 시스템은 해당 scope를
   사용자 동의 목록에 추가하고 갱신 시각을 기록해야 한다 (SHALL).
2. WHEN 사용자가 특정 scope의 동의를 철회하면 THEN 시스템은 해당 scope만 제거하고 다른 scope는
   보존해야 한다 (SHALL).
3. WHEN 동의 상태를 조회하면 THEN 시스템은 알려진 scope별 부여 여부(true/false)를 반환해야 한다 (SHALL).
4. IF 알 수 없는 scope 이름이 들어오면 THEN 시스템은 이를 거부(400)해야 한다 (SHALL).
5. WHILE 동의가 변경되는 동안 시스템은 기존 추천·알림 게이트(동의 차등) 동작을 그대로 유지해야 한다 (SHALL).

### 요구사항 2: DSR — 접근/내보내기(access·export)

**User Story:**
데이터 주체로서, 나에 대해 보관된 데이터를 한 번에 받아보기를 원한다,
그래서 어떤 정보가 저장돼 있는지 확인할 수 있다(GDPR 제15·20조).

**수용기준 (Acceptance Criteria):**
1. WHEN 접근 요청이 들어오면 THEN 시스템은 해당 `user_id`로 키잉된 데이터(프로필·동의·주문·대화
   메모리·미해결 스레드·engagement)를 모아 단일 구조로 반환해야 한다 (SHALL).
2. WHEN 내보내기를 요청하면 THEN 시스템은 직렬화 가능한(JSON) 형태로 전체 데이터를 반환해야 한다 (SHALL).
3. IF 해당 사용자에 데이터가 없으면 THEN 시스템은 빈(그러나 형태가 보존된) 결과를 반환해야 한다 (SHALL).

### 요구사항 3: DSR — 삭제(delete, 잊힐 권리)

**User Story:**
데이터 주체로서, 내 데이터의 삭제를 요청하기를 원한다,
그래서 더 이상 보관되지 않게 할 수 있다(GDPR 제17조).

**수용기준 (Acceptance Criteria):**
1. WHEN 삭제 요청이 들어오면 THEN 시스템은 해당 `user_id`로 키잉된 모든 저장소 데이터를 best-effort로
   삭제하고, 저장소별 삭제 결과 요약을 반환해야 한다 (SHALL).
2. IF 어떤 저장소가 삭제 메서드를 제공하지 않으면 THEN 시스템은 그 저장소를 건너뛰되 전체 흐름을
   막지 않아야 한다(부분 삭제 허용·요약에 표기) (SHALL).
3. WHEN 삭제가 완료되면 THEN 시스템은 같은 사용자에 대한 후속 접근 요청이 빈 결과를 반환하도록 해야 한다 (SHALL).

### 요구사항 4: DSR — 정정(rectify)

**User Story:**
데이터 주체로서, 잘못된 프로필 정보를 바로잡기를 원한다,
그래서 정확한 정보가 유지되게 할 수 있다(GDPR 제16조).

**수용기준 (Acceptance Criteria):**
1. WHEN 정정 요청(허용된 필드)이 들어오면 THEN 시스템은 해당 사용자 프로필의 그 필드를 갱신해야 한다 (SHALL).
2. IF 허용되지 않은 필드를 정정하려 하면 THEN 시스템은 이를 거부(400)해야 한다 (SHALL).

### 요구사항 5: 데이터 보존(retention) 정책 + 만료 스윕(Mock)

**User Story:**
운영자로서, 데이터 보존 기한과 만료 처리 인터페이스를 갖기를 원한다,
그래서 기한 경과 데이터를 일관된 정책으로 정리할 수 있다(GDPR 제5조 저장 제한).

**수용기준 (Acceptance Criteria):**
1. WHEN 보존 정책을 조회하면 THEN 시스템은 데이터 카테고리별 보존 기한(일)을 반환해야 한다 (SHALL).
2. WHEN 만료 스윕을 실행하면 THEN 시스템은 (Mock 기준) 만료 대상 후보 건수를 카테고리별로 보고해야 한다 (SHALL).
3. WHILE 스윕이 Mock인 동안 시스템은 실제 데이터를 변형하지 않고 인터페이스만 제공해야 한다(회귀 불변) (SHALL).

### 요구사항 6: 감사(audit) 훅

**User Story:**
보안 담당자로서, 보안적으로 의미 있는 개인정보 이벤트가 기록되기를 원한다,
그래서 사후 추적·감사를 할 수 있다(GDPR 제30조 처리 활동 기록).

**수용기준 (Acceptance Criteria):**
1. WHEN 동의 변경·DSR(접근·삭제·정정)·스윕이 발생하면 THEN 시스템은 감사 이벤트(행위·주체·시각)를
   기록해야 한다 (SHALL).
2. WHEN 감사 로그를 조회하면 THEN 시스템은 기록된 이벤트 목록을 시간순으로 반환해야 한다 (SHALL).
3. IF 감사 sink가 실패하면 THEN 시스템은 주 흐름을 막지 않아야 한다(비차단) (SHALL).

### 요구사항 7: 회귀 불변(추가형)

**User Story:**
개발자로서, 본 스트림이 기존 기능을 바꾸지 않기를 원한다,
그래서 안전하게 점진 도입할 수 있다(스트랭글러).

**수용기준 (Acceptance Criteria):**
1. WHEN 새 라우터를 등록하면 THEN 시스템은 기존 엔드포인트·도메인/Repository 시그니처를 변경하지
   않아야 한다 (SHALL).
2. WHILE 본 스트림이 로드되는 동안 전체 테스트 스위트(회귀 포함)는 green이어야 한다 (SHALL).
