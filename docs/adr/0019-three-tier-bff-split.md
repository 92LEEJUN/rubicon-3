# ADR-0019: 3계층(FE/BFF/BE) + BFF 독립 서비스 분리

- **상태**: 채택
- **관련**: `docs/architecture.md` §8·§9, `docs/api-contract.md` §1·§2.4

## 배경
클라이언트 표면(WS·HTTP·aggregation·인증)과 도메인 로직의 책임을 어떻게 배치할지. **초기 MVP 판단은 "통합 유지"**였다.

## 후보안
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A | **통합 단일 서비스**(FE-BE 직접 또는 1개 백엔드) | 단순·단일 배포 | 팀 독립성·표현/도메인 분리 스케일 어려움 |
| **B (선택)** | **3계층 + BFF 독립 서비스** — FE→BFF→BE 내부 API | 팀·계약 독립, 표현층 독립 배포, 2nd 클라이언트 대비, 계약 두 겹으로 누수 차단 | 서비스 2개 운영 |

## 결정
**B.** BFF가 클라이언트 API 표면 소유(aggregation·Template 변환·스트리밍 중계·인증 게이트), **비즈니스 로직 없음**. BE 도메인을 내부 API로 호출. 계약: 클라↔BFF(§2) / BFF↔BE(§2.4) 분리.

## 기각 이유 / 전환
- A: 이번 빌드는 **FE/BFF/BE를 독립 브랜치·워크스트림**으로 개발 → "통합 유지"에서 분리로 **전환**(트리거 "팀·계약 소유권 분리" 충족).
- **역트리거**: 운영 복잡도가 분리 이득을 넘으면 재통합 검토(경계 명확 → 합치는 비용 낮음).

## 결과/영향
라우팅 판단은 BE 소유(ADR-0024). 라우팅·계약의 단일 출처는 architecture/api-contract.
