# 요구사항 (Requirements) — 멀티테넌트 상태 + 영속화

## 개요
내부 API는 현재 **단일 User(`usr_01`)가 빌드 타임에 박힌 전역 컨테이너**로 동작한다(모든 사용자가
같은 기기·주문·대화기억을 공유). 본 작업은 **사용자별 상태를 격리**하고 **DB로 영속화**해, 여러
사용자가 동시에 안전하게 쓰면서 재시작에도 상태가 보존되도록 한다. 공유 참조데이터(상품·CS·거점)는
중복 없이 공유한다. 격리 모델(A: 사용자별 컨테이너 / B: 공유무상태+사용자별상태)은 design에서
비교·결정한다. 기반 문서 [operations.md](../../docs/operations.md)·[data-model.md](../../docs/data-model.md)
위에서 설계한다.

## 요구사항 목록

### 요구사항 1: 사용자별 상태 격리
**User Story:**
서비스 운영자로서, 각 사용자의 상태가 서로 격리되기를 원한다, 그래서 한 사용자가 다른 사용자의
기기·주문·대화·추천 상태를 보거나 바꾸지 못하게 할 수 있다.

**수용기준:**
1. WHEN 사용자 A의 턴/조회/커밋을 처리할 때 THEN 시스템은 **A의 상태만** 읽고 써야 한다 (SHALL).
2. WHEN 사용자 B가 동일 엔드포인트를 호출할 때 THEN 시스템은 A의 어떤 상태도 B에게 노출하지 않아야 한다 (SHALL).
3. 격리 대상 상태는 **기기·주문이력·대화기억(companion)·미해결 스레드(open-loop)·추천억제(engagement)·알림·사용자 프로필**을 포함해야 한다 (SHALL).

### 요구사항 2: 요청 신원 컨텍스트
**User Story:**
BFF 통합 개발자로서, 검증된 사용자 신원을 요청마다 내부 API에 전달하기를 원한다, 그래서 모든
턴·조회·커밋이 올바른 사용자에 귀속되게 할 수 있다.

**수용기준:**
1. WHEN WS `/internal/turn` 연결/메시지 또는 HTTP 요청이 들어올 때 THEN 시스템은 **요청이 운반한 user_id**로 상태를 해석해야 한다 (SHALL).
2. IF 요청에 user_id가 없으면 THEN 시스템은 **명시적 기본 사용자**로 폴백하되(회귀 보존), 그 경계를 문서화해야 한다 (SHALL).
3. 인증은 BFF가 담당하고 내부 API는 전달된 신원을 신뢰한다([api-contract](../../docs/api-contract.md) §2.4) (SHALL).

### 요구사항 3: 공유 참조데이터 일관성
**User Story:**
사용자로서, 상품·CS 가이드·거점/재고 같은 참조데이터가 누구에게나 동일하기를 원한다, 그래서
사용자마다 다른 카탈로그를 보는 불일치가 없게 할 수 있다.

**수용기준:**
1. WHEN 임의 사용자가 추천·진단·거점 조회를 할 때 THEN 시스템은 **단일 공유 참조데이터**를 사용해야 한다 (SHALL).
2. 시스템은 참조데이터를 사용자별로 중복 보관하지 않아야 한다 (SHALL). _(격리 모델이 중복을 유발하면 design에서 그 비용을 명시)_

### 요구사항 4: 상태 영속화(DB)
**User Story:**
서비스 운영자로서, 사용자별 상태가 재시작/인스턴스 교체에도 보존되기를 원한다, 그래서 진행 중
주문·대화 맥락이 사라지지 않게 할 수 있다.

**수용기준:**
1. WHEN 프로세스가 재시작될 때 THEN 시스템은 영속된 사용자 상태(주문·대화기억·개인화)를 복원해야 한다 (SHALL).
2. 시스템은 **기존 Repository/Port 인터페이스를 유지**하고 인메모리↔DB 어댑터를 교체 가능해야 한다([data-model](../../docs/data-model.md), 스트랭글러) (SHALL).
3. WHILE DB가 일시 불가일 때 시스템은 안전하게 실패(에러 봉투/5xx)하고 데이터 손상을 남기지 않아야 한다 (SHALL).

### 요구사항 5: 동시성 안전
**User Story:**
사용자로서, 동시에 여러 요청이 와도 내 상태가 깨지지 않기를 원한다, 그래서 주문/예약 같은
커밋이 경합에서 일관되게 처리되게 할 수 있다.

**수용기준:**
1. WHEN 같은 사용자의 요청이 동시에 처리될 때 THEN 시스템은 read-modify-write(예: 주문 체크아웃·픽업 전이)의 **원자성**을 보장해야 한다 (SHALL).
2. WHEN 서로 다른 사용자의 요청이 동시에 처리될 때 THEN 시스템은 상태 간섭 없이 독립 처리해야 한다 (SHALL).

### 요구사항 6: 세션 vs 사용자 키 분리
**User Story:**
개발자로서, 대화 세션 상태와 사용자 도메인 상태가 올바른 키로 분리되기를 원한다, 그래서 한
사용자의 여러 대화가 서로 또는 도메인 상태와 섞이지 않게 할 수 있다.

**수용기준:**
1. 시스템은 **대화 블랙보드를 session_id로, 도메인 상태를 user_id로** 분리 보관해야 한다 (SHALL).
2. WHEN 한 사용자가 여러 세션을 가질 때 THEN 세션 블랙보드 carry가 세션 간 누수되지 않아야 한다 (SHALL). _(기존 세션 격리 회귀 유지)_

### 요구사항 7: 회귀 불변(스트랭글러)
**User Story:**
유지보수자로서, 멀티테넌트 전환이 기존 단일 사용자 동작을 깨지 않기를 원한다, 그래서 점진적으로
안전하게 이행할 수 있다.

**수용기준:**
1. WHEN 멀티테넌트/DB 기능을 끈 기본 상태일 때 THEN 시스템은 **오늘의 §2.1 봉투·엔드포인트 동작과 동일**해야 한다 (SHALL).
2. 전환은 **토글/어댑터 교체**로 이루어지고 각 단계 후 전체 테스트가 green이어야 한다 (SHALL).
3. 기존 테스트(단일 기본 사용자 전제)는 통과를 유지해야 한다 (SHALL).
